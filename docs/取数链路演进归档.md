## 1. 三代链路总览

```text
第一代（legacy）     第二代（过渡兼容层）           第三代（正式链路）
FeatureManager       BatchFactorEngine              BatchFactorEngine
Calculator/Executor    + FeatureStoreDataProvider     + SmartQuantDataProvider
DataRouter             （适配旧 Store/Router）        （任务级独立 Provider）
FeatureStore 绑定取数   仍优先绑定 Store               与 Store 解绑
     ↓ 2026-08-03 新引擎引入 DataProvider 契约 ↓ 2026-08-11 独立 Provider 落地
```

演进主线有两条：

1. **路由升级**：`DataRouter`（字符串键解析 + 单项读取）升级为原生实现
   DataProvider 五方法契约的 `SmartQuantDataProvider`（Catalog 描述 + 物理绑定 +
   数据集级批量读取）；
2. **Store 解绑**：取数从“必须携带 `FeatureStore`、坐标轴由 snapshot 固化、
   物化特征优先”演变为“Provider 任务级自建日历与资产轴、唯一依据 Catalog、
   不经过 Store”。

## 2. 第一代：legacy 取数链路（Store 绑定）

代码位置（原 `factor_engine/data/`，2026-08-18 清理后归入 `legacy/`）：

- [`factor_engine/legacy/`](../src/factor_engine/legacy/)：`FeatureManager`、
  `Calculator`、`Executor`、`FeatureRegistry`（公式以 JSON 定义注册）；
- [`factor_engine/legacy/data/`](../src/factor_engine/legacy/data/)：`FeatureStore`
  （[`store.py`](../src/factor_engine/legacy/data/store.py)）、`DataRouter`
  （[`router.py`](../src/factor_engine/legacy/data/router.py)）、`SmartQuantSourceReader`
  （[`smartquant.py`](../src/factor_engine/legacy/data/smartquant.py)）、配置解析
  （[`sources.py`](../src/factor_engine/legacy/data/sources.py)）、数组封装
  （[`alignment.py`](../src/factor_engine/legacy/data/alignment.py)）与对象契约
  （[`model.py`](../src/factor_engine/legacy/data/model.py)）。

调用链：

```text
FeatureManager.execute(ExecutionRequest)
  -> FeatureRegistry.resolve(target)              公式定义
  -> Calculator(store, data_router=router)
     -> Executor._load_feature_like(key)          叶子取数优先级：
        1. 本次运行 runtime_features
        2. store.has_feature(key) -> store.load_feature()
        3. data_router.read(key, store)           未物化才走 Router
  -> DataRouter.resolve_source(key)               memory > overrides > sources 记录 > data_dict 扫描
  -> DataRouter.read_spec(spec, store)            source="store" 回 Store，
                                                  "memory" 走内存，其余交 Reader
  -> SmartQuantSourceReader.read_source(spec, store)
     -> FeatureArray（T x N x S + FeatureSpace + missing_value 协议）
```

这一代取数与 `FeatureStore` 强绑定，具体表现为：

1. **store 是取数 API 的必传参数**：`DataRouter.read/read_spec/load_many` 与
   `SmartQuantSourceReader.read_source` 都接收 `store`，Reader 用它
   `resolve_space()` 得到统一的日期、代码和 step 坐标；
2. **坐标轴由 snapshot 固化**：`FeatureStore.init_snapshot()` 查询并持久化
   交易日历轴和各资产 master axis 到 manifest，之后所有取数、计算和物化共享
   这套冻结坐标；分钟代码映射也来自 snapshot 的 `code_map_path`；
3. **缓存身份包含 store 版本**：Router 读取缓存键是
   `stable_hash(spec, store.snapshot_signature, scope)`，取数结果与 snapshot
   版本绑定；
4. **物化特征本身是一种数据源**：`resolve_source` 允许 `source="store"`，
   Router 读取时先分派回 `store.load_feature()`，计算结果落盘后可被后续公式
   当输入直接复用。

该代数据契约是 `FeatureArray`（`data/model.py`），与坐标空间对象
`FeatureSpace`、执行范围 `ExecutionScope` 配套。

## 3. 第二代：过渡兼容层 FeatureStoreDataProvider（已移除）

> 2026-08-18 起该类已从 `providers.py` 删除，相关测试、README 迁移节与示例
> notebook 同步迁移；本节仅保留历史描述。

2026-08-03 新 batch engine 引入统一的 DataProvider 契约
（[`model.py`](../src/factor_engine/model.py) 中的 `DataProvider` Protocol）：

```text
calendar_dates(calendar)
asset_codes(asset_type, dates, selector)
describe_many(source_refs)
bind_many(source_terms, read_domain)
load_many(bindings)
```

`FeatureStoreDataProvider`（[`providers.py`](../src/factor_engine/providers.py)）
把第一代的 Store + Router 适配到这五个方法，是“Store 绑定取数”在新契约下的最后
形态：

- `calendar_dates()` / `asset_codes()` 仍取自 `store.get_dates()` /
  `store.get_asset_codes()`，即坐标轴仍依赖 snapshot；
- `bind_many()` 保持第一代的绑定优先级：先查 `store.has_feature(key)`，命中则
  绑定 `source="store"`；未命中才调用 `DataRouter.resolve_source(key)`；
- `load_many()` 委托 `DataRouter.load_many(specs, store)` 或
  `store.load_feature()`，再把 `FeatureArray` 转换为新引擎要求的
  `float64 ndarray`，并校验返回日期顺序和代码位置。

两个需要记住的边界：

- 这一代的 `DataRouter.load_many()` 只是对单项 `read_spec()` 的循环回退，没有
  真正的数据集级 I/O 合并；
- 对象契约当时已经统一：`SourceSpec` 始终定义在
  [`model.py`](../src/factor_engine/model.py)，legacy
  [`legacy/data/model.py`](../src/factor_engine/legacy/data/model.py) 只是
  re-export 它；`FeatureArray`、`ExecutionScope` 等坐标对象才是 legacy 专属。
  兼容层的主要工作是在 `FeatureArray` 与新 Runtime 的 `float64 ndarray`
  契约之间转换。

同文件中的 `MemoryDataProvider` 是契约测试与小任务的内存实现，不属于演进中的
过渡形态，至今仍是新引擎单元测试的基准 Provider。

## 4. 第三代：正式链路 SmartQuantDataProvider（Store 解绑）

2026-08-11 起，正式取数链路改由
[`data_provider/`](../src/factor_engine/data_provider/) 子包原生实现，内部按
职责划分：

| 模块 | 职责 |
| --- | --- |
| [`catalog.py`](../src/factor_engine/data_provider/catalog.py) | Catalog 解析、`describe`/`bind`、稳定字段 ValueKind 规则 |
| [`datasets.py`](../src/factor_engine/data_provider/datasets.py) | 特殊 Source 的 SQL 约定与 LoadGroup 批量读取 |
| [`backend.py`](../src/factor_engine/data_provider/backend.py) | OceanBase / DuckDB 中性后端、查询计时 |
| [`normalize.py`](../src/factor_engine/data_provider/normalize.py) | 批量结果的 `float64 T x N x S / NaN` 规范化与契约校验 |
| [`smartquant.py`](../src/factor_engine/data_provider/smartquant.py) | 任务级协调器，实现五个 Provider 方法 |

与第一、二代的关键差异：

- **坐标轴任务级自建，不落盘**：calendar 直接查询
  `SmartQuant.JY_TradingDayNew`；资产轴在 Compiler horizon 预分析后，按
  任务 read horizon 从对应行情表解析并在 Provider 内冻结（同一任务重复请求
  不同参数会直接报错），不再经过 snapshot；
- **Bind 只依据 Catalog**：`bind_many()` 通过 `catalog.bind(ref)` 组装
  `SourceSpec` 与 LoadGroup 键，不存在“先查 Store 再回退 Router”的分支，
  Store 概念完全退出取数路径；
- **真正的批量读取**：相同物理数据集、相同 ReadDomain 和兼容查询语义的字段
  组成一个 LoadGroup，日频宽表一次 SQL 读多列，分钟 parquet 一次 scan 加列
  裁剪；
- **数据契约直达 Runtime**：`load_many()` 直接返回 `term_id -> float64
  T x N x S ndarray`，不再经过 `FeatureArray`；
- **诊断随 Provider**：物理查询、缓存命中、耗时等事件记录在
  `provider.diagnostics`，最终并入 `ExecutionStats.provider_events`。

配置层面，第三代与第一代共用同一份物理目录配置；2026-08-18 清理后该配置归
正式链路所有，位于
[`data_provider/data_sources.json`](../src/factor_engine/data_provider/data_sources.json)
（Catalog 要求 `schema_version = 2`），legacy Router 读取同一文件。代码层面，
唯一保留的共享点是中性的 SQL 后端——legacy 的 `SmartQuantSourceReader` 也复用
`data_provider.backend.OceanBaseBackend`，除此之外正式链不依赖 Store、Router、
旧 Reader 或 `FeatureArray`。

已保存因子的取数不属于基础 Provider：`factor:` 前缀的 Source 引用由
[`repository.py`](../src/factor_engine/repository.py) 的
`RepositoryDataProvider` 组合任意基础 Provider 与
`TemporaryFactorRepository` 完成，保持与正式 FactorRepository 的边界独立。

## 5. 绑定关系对比

| 维度 | 第一代 legacy | 第二代兼容层 | 第三代正式 |
| --- | --- | --- | --- |
| 日历/资产轴来源 | `init_snapshot()` 落盘固化 | 同左（`store.get_dates/get_asset_codes`） | Provider 任务级查询并冻结 |
| 取数入口签名 | `read(key, store)`、`read_source(spec, store)` | Provider 五方法，内部仍传 store | Provider 五方法，无 store 参数 |
| 绑定优先级 | 物化 Store 优先，Router 回退 | 同左（`bind_many` 保留该顺序） | 唯一依据 Catalog |
| 缓存身份 | `stable_hash(spec, snapshot_signature, scope)` | 关闭 Router 缓存，按分区读取 | 任务级缓存，随 Provider 生命周期释放 |
| 批量能力 | 单项读取 | 单项读取循环 | LoadGroup 数据集级批量 |
| 返回契约 | `FeatureArray` | `FeatureArray` -> ndarray | 直接 `float64 T x N x S` |
| 落盘设施角色 | 坐标基准 + 物化复用 + 读取分派 | 坐标基准 + 优先绑定 | 不参与基础取数；因子保存走独立 Repository |
