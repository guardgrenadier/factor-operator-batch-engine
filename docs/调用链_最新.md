## 2. 推荐入口

一次完整计算由四个显式对象组成：

```python
from factor_engine import (
    BatchFactorEngine,
    ComputeRequest,
    DomainSpec,
    ExecutionOptions,
    FormulaBatch,
)

batch = FormulaBatch.from_text(
    common_inputs="""
        close = source("stk.1d.close")
        volume = source("stk.1d.volume")
    """,
    formulas={
        "alpha": """
            mean = ts_mean(close, 5)
            factor = mean / volume
        """,
    },
)

request = ComputeRequest(
    domain=DomainSpec(
        start="20240101",
        end="20241231",
        asset_scope={"stk": "all"},
        target_asset="stk",
        target_freq="1d",
        target_step_count=1,
    ),
    batch=batch,
)

engine = BatchFactorEngine(provider)
result = engine.compute(request, options=ExecutionOptions(chunk_size=20))
```

职责划分：

```text
FormulaBatch
  描述一批公式及其名称作用域

DomainSpec
  描述任务输出区间、资产范围、目标频率和目标 step 数

ComputeRequest
  把“算什么”和“在哪个 Domain 上算”组合起来

ExecutionOptions
  只描述本次怎样执行；第一版只有 chunk_size

DataProvider
  向 Compiler 描述输入的原生 frequency/step/asset Domain
  向 Runtime 绑定并加载物理输入

BatchFactorEngine
  统一协调 compile、stream 和 compute
```

## 3. 总体调用链

### 3.1 完整结果路径：compute

```text
FormulaBatch.from_text()
  -> FormulaParser.parse_program()
     -> Python ast.parse()
     -> Surface AST：SymbolRefExpr / HelperExpr / OperatorExpr / LiteralExpr

ComputeRequest(DomainSpec, FormulaBatch)
  -> BatchFactorEngine.compute()
     -> BatchFactorEngine.stream()
        -> BatchFactorEngine.compile()
            -> Compiler.compile()
               -> FormulaBatch.bind()
               -> helper 展开
               -> lookback 预分析（pre_lookback）
               -> DataProvider.describe_many()
               -> output domain 解析（资产轴日期窗口包含 lookback）
               -> AST lowering + operator domain_rule + 跨公式 CSE
               -> 输出 Domain 的 singleton 可广播性校验
               -> job_lookback 与 pre_lookback 一致性校验
               -> LogicalPlan + CompiledJob
        -> PhysicalPlanner.partitions()
        -> Runtime.execute_partition()
           -> DataProvider.bind_many()
           -> 按 load_group_key 分组
           -> DataProvider.load_many()
           -> 按拓扑顺序执行 Term DAG
           -> 每个 operator 结果校验其原生 TermDomain shape
           -> 释放不再使用的 workspace 值
           -> 最终输出按 NumPy singleton 规则广播到任务 shape
           -> yield ResultChunk
        -> ResultStream
     -> 按 output_slice 装配每个公式的完整 ndarray
     -> ComputeResult
```

`compute()` 没有第二套计算逻辑。它只是创建并完整消费 `stream()`，把 chunk 写入最终数组。

### 3.2 流式路径：stream

```python
stream = engine.stream(request, options=ExecutionOptions(chunk_size=20))

for chunk in stream:
    consume(chunk.formula_id, chunk.output_slice, chunk.values)
```

```text
BatchFactorEngine.stream()
  -> 编译一次
  -> 规划全部日期分区
  -> 创建共享 Runtime 和 ExecutionStats
  -> 按 partition 顺序执行
  -> 每个 partition 按 plan.outputs 顺序产生 ResultChunk
```

`ResultStream` 只能消费一次。只有底层迭代器自然结束时，`stream.succeeded` 才会变为 `True`。因此流中途拿到的 chunk 都是 provisional 结果，消费者不能把“收到最后一个已知 chunk”等同于“任务成功提交”。

### 3.3 只编译路径：compile

```python
job = engine.compile(request)
```

该路径不绑定物理 `SourceSpec`，也不读取数组。输出是：

```text
CompiledJob
  ├── domain: ResolvedOutputDomain
  └── plan: LogicalPlan
      ├── terms
      ├── topological_order
      ├── outputs
      ├── reference_counts
      ├── job_lookback
      └── semantic_id
```

这是 review 编译结果、公共子表达式消除和 lookback 的最直接入口。

## 4. 公式解析与名称绑定

文件：[`formula.py`](../src/factor_engine/formula.py)

### 4.1 from_text

```text
FormulaBatch.from_text(common_inputs=..., formulas=...)
  -> 创建一个 FormulaParser
  -> common_inputs 解析为一个 FormulaProgram
  -> 每个 formula_id 的文本分别解析为 FormulaProgram
  -> FormulaBatch(common_inputs, formulas)
```

每个程序只允许简单赋值：

```python
name = expression
```

Parser 使用 Python `ast` 做语法解析，但只接受引擎支持的语法子集。解析后的主要节点是：

```text
LiteralExpr
  字面量

SymbolRefExpr
  尚未绑定的程序内名称，例如 close、mean

SourceRefExpr
  已经明确的逻辑输入引用

OperatorExpr
  运算符调用或由 Python 运算符转换出的调用

HelperExpr
  source/get_lf/get_hf/load_factor 等编译期 helper
```

字符串中的 `close + volume` 会转换成 `OperatorExpr("add", ...)`，不会在 parse 阶段执行 NumPy。
`resample(...)` 在 parse 阶段就是公开 `OperatorExpr("resample")`，不与取数 helper 共用分类。

### 4.2 bind

```text
Compiler.compile()
  -> FormulaBatch.bind(reserved_names=operators + helpers)
     -> 先顺序绑定 `common_inputs`
     -> 再分别绑定每个公式程序
     -> SymbolRefExpr 替换成它指向的 Expr
     -> 每个公式最后一个 binding 的表达式成为该 formula_id 的输出
```

作用域规则在 `_bind_program()` 和 `_resolve_symbols()` 中集中实现：

- `common_inputs` 对所有公式可见；
- 一个公式可引用本公式前面定义的局部名称；
- 禁止前向引用；
- 禁止跨公式引用另一个公式的局部名称；
- 禁止局部名称覆盖 common input；
- 禁止使用 helper 或 operator 名称作为 binding 名；
- binding 名只用于展开作用域，不进入最终 Term 的结构身份。

因此以下两个局部命名不同的公共表达式仍可在编译时合并：

```text
formula A: x = close + volume
formula B: y = close + volume
```

### 4.3 直接 AST 入口

调用方也可以使用 `source()`、`get_lf()`、`get_hf()`、`get_fund()`、`load_factor()` 和
`operator()` 构造同一套不可变 AST。包括 `resample` 在内的普通算子都通过
`operator(name, ...)` 构造；这些函数不读取数据、不访问 Registry，也不改变全局状态。

`parse_formula_batch()` 只是“一行一个 `formula_id = expression`”的轻量适配器，最终仍调用 `FormulaBatch.from_text()`，没有独立语义。

## 5. 编译调用链

文件：[`compiler.py`](../src/factor_engine/compiler.py)

### 5.1 Compiler.compile 总顺序

```text
Compiler.compile(request)
  1. FormulaBatch.bind()
  2. _expand_helpers()
  3. lookback 预分析：对每个输出用 _expression_lookback() 求累计回看，
     取最大值 pre_lookback（与正式 lowering 共用参数规范化规则）
  4. 收集所有 SourceRefExpr，并按引用身份去重
  5. provider.describe_many(refs) -> InputSpec
  6. _resolve_domain(DomainSpec, InputSpecs, pre_lookback)
  7. 逐个输出 _lower(expr)，由 OperatorSpec.domain_rule 推导中间 Domain
  8. 校验每个输出 Term 的原生 Domain 可以广播到 target domain
  9. 统计 Term reference_counts
 10. 取所有输出的最大 lookback 为 job_lookback；
     若与 pre_lookback 不一致，抛 CompileError
 11. 生成 plan.semantic_id
 12. 返回 CompiledJob(LogicalPlan, ResolvedOutputDomain)
```

### 5.2 helper 展开

`HelperExpr` 不会进入 LogicalPlan。`_expand_helpers()` 在 lowering 前把它改写成规范 AST。
注册的 helper 仅包括 `source` / `get_lf` / `get_hf` / `get_fund` / `load_factor` /
`select_asset` / `select_index_feature` / `index_member_stat` / `project_stk_to_cb`：

```text
source("stk.1d.close")
  -> SourceRefExpr("stk.1d.close")

get_lf("stk", "close") / get_fund("stk", "close")
  -> SourceRefExpr("stk.1d.close")

get_hf("stk", "5min", "close")
  -> SourceRefExpr("stk.5min.close")

get_hf("stk", "1min", "close", resample="15min", method="last")
  -> SourceRefExpr("stk.1min.close")
  -> OperatorExpr("resample", target_freq="15min", method="last")

load_factor("alpha")
  -> SourceRefExpr("factor:alpha")

project_stk_to_cb(values)
  -> 自动注入 SourceRefExpr("cb.1d.underlying_stk")
  -> Source 按 cb ReadDomain 绑定 CBStockMap
  -> _cb_stock_map() 使用任务 axes["stk"] 生成股票列位置
  -> Runtime 执行 lookup_by_col(values, mapping)
  -> T × N_cb × S

select_asset(values, 101)
  -> OperatorExpr("__select_asset", code=101)

select_index_feature(values, "000300")
  -> OperatorExpr("__select_asset", code="000300", expected_asset_type="idx")
  -> code -> pos -> select_by_pos
  -> T × 1 × S

index_member_stat(values, member, method="mean")
  -> OperatorExpr("member_mean", values, member)
  -> T × 1 × S
```

`resample(...)` 与 `align_frequency(...)` 是公开算子调用，不是 helper：它们在 parse
阶段直接产出 `OperatorExpr`，`_expand_helpers()` 对其只递归透传、不改写，合法性由
§5.8 的专属 lowering 校验：

```text
resample(x, "1d", method="mean")
  -> OperatorExpr("resample", target_freq="1d", method="mean")
  -> lowering: OperatorTerm("resample", ...)

align_frequency(x, "1min", method="ffill")
  -> OperatorExpr("align_frequency", ...)
```

指数特征和成分 mask 均由用户显式声明 Source；两个指数 helper 不注册隐式
Source，也不创建完整目标资产轴的广播数组。

这里的 helper 只表达语义便利写法；真正的合法性检查和对齐改写仍由后续 lowering 完成。

### 5.3 InputSpec：逻辑引用与物理取数之间的编译期适配层

```text
SourceRefExpr
  公式中的稳定逻辑引用：logical_key + semantic_params

DataProvider.describe_many()
  只描述，不加载

InputSpec
  asset_type / frequency / step_count / value_kind / calendar
```

Compiler 只依赖 `InputSpec` 判断 source 的 domain 和类型，不需要知道 source 最终来自内存、FeatureStore、数据库还是临时因子仓库。

`SourceSpec` 此时尚未产生，因此物理表名、字段和 reader 配置不会污染 `LogicalPlan.semantic_id`。同一逻辑任务切换等价的物理 load group，逻辑计划身份不变。

### 5.4 output domain 解析

```text
_resolve_domain(spec, input_specs, pre_lookback)
  -> 校验 target_asset 已声明在 asset_scope
  -> 从 InputSpec 确定唯一 calendar
  -> provider.calendar_dates(calendar)
  -> 截取 start 到 end 的输出日期
  -> 用 pre_lookback 向前扩展输出日期窗口得到 axis_dates
  -> 校验所有 InputSpec 的 asset_type 均已声明在 asset_scope
  -> provider.asset_codes(asset, axis_dates, selector) 获取各资产 master axis
  -> 对每种资产应用 "all" 或显式子集
  -> 根据 target_freq + target_step_count 生成 step axis
  -> 生成 axis_fingerprint
  -> ResolvedOutputDomain
```

`asset_scope={"stk": "all"}` 指 provider 在本任务编译时对按 lookback 扩展后的日期窗口
返回的完整有序 master axis，不是“日期区间内至少出现过一次的代码并集”。显式子集保留调用方顺序，重复或未知代码直接失败。

当前 domain 身份不只看 shape。资产类型、代码顺序、频率、step 数、calendar 和 axis fingerprint 共同参与 Term domain，因此两个完整资产轴即使 shape 相同，坐标身份不同也不能直接混合；明确的 singleton 轴除外。

这里需要区分三个相关但不同的对象：

```text
DomainSpec
  调用方声明的目标：日期区间、asset_scope、target_asset、target_freq、target_step_count

ResolvedOutputDomain
  编译期冻结后的最终坐标：dates、codes、steps、calendar、axis_fingerprint

TermDomain
  每个中间 Term 的原生坐标：asset identity、frequency、step_count、calendar
```

`frequency` 与 `step_count` 是两个独立字段。日频行情通常是 `1d + 1 step`，日频基本面可以是 `1d + Q steps`；step selection/reduce 可以改变 `step_count` 而不改变 `frequency`。

完整资产轴的 `TermDomain.codes` 保存真实有序代码。截面或成员池 reduce 没有某一只真实资产坐标，因此使用 `codes=None` 表示匿名 singleton，其 `asset_count` 仍为 1。标量字面量则完全没有 `TermDomain`，即 `domain=None`。

### 5.5 AST lowering、CSE 和稳定身份

`_lower()` 只接收 helper 已展开、symbol 已绑定的规范 AST：

```text
LiteralExpr -> LiteralTerm
SourceRefExpr -> SourceTerm
OperatorExpr -> OperatorTerm
```

三类 Term 的 Domain 来源不同：

```text
LiteralTerm
  scalar -> domain=None

SourceTerm
  原样保留 InputSpec 的 asset_type / frequency / step_count / calendar
  使用本任务冻结的对应资产 codes 与 axis_fingerprint

OperatorTerm
  由 OperatorSpec.domain_rule 根据输入 TermDomain 和字面量参数推导
  未指定专用规则时使用 numpy_domain
```

每个 Term 先根据真实语义生成稳定 hash，再经过 `_intern()`：

```text
semantic key 已存在
  -> 复用已有 term_id

semantic key 不存在
  -> 创建新 Term
  -> 追加到 topological_order
```

因此同批次所有公式共同 lower 到一个 DAG，重复 source 和公共子表达式只保留一个 Term。CSE 是语义 hash 的自然结果，不依赖用户局部变量名。

### 5.6 operator 校验与 lookback

普通 operator lowering 会：

```text
从 operator registry 取 OperatorSpec
  -> _canonical_call() 先按算子函数 Python signature 绑定并拒绝不匹配调用，
     再区分数据输入与字面量配置（变长输入算子的全部实参都是无名数据输入）
  -> 递归 lower 输入
  -> _validate_operator() 校验输入个数和 ValueKind
  -> 调用专用 domain_rule 或默认 numpy_domain
  -> 推导并校验输出 TermDomain
  -> 推导 output ValueKind
  -> 计算 lookback
  -> 创建或复用 OperatorTerm
```

Term 的 lookback 是：

```text
operator 自身 date_lookback + 所有输入中的最大累计 lookback
```

最终 `job_lookback` 是全部输出 Term 的最大值。第一版 PhysicalPlanner 对所有 source 和分区统一使用这个任务级最大值，尚未做 per-Term 日期裁剪。

无界日期前向填充无法得到有限 lookback，因此 batch 编译会拒绝未指定 `limit` 的 date-axis `ffill`/`ts_ffill`。

### 5.7 普通 operator 的 Domain 推导

普通 operator 不再由 `_lower()` 写死统一对齐逻辑，而是通过 `OperatorSpec.domain_rule` 声明坐标语义。没有专用规则时使用 `numpy_domain`：

```text
输入 TermDomain 列表
  -> 过滤 domain=None 的 scalar
  -> 校验所有 calendar 一致，不一致即 DomainError
  -> 独立合并时间/step 轴
  -> 独立合并资产轴
  -> 输出 TermDomain
```

时间与第三维规则：

```text
step_count 相同        -> 保持该 step_count
1 与 S                 -> singleton 广播，输出 S
M 与 N，均不为 1       -> DomainError

frequency 相同         -> 直接合并
1d/step=1 与一个分钟频 -> 允许 singleton 广播，输出分钟频
其他不同 frequency     -> DomainError，要求显式对齐
```

资产轴规则：

```text
完整轴与相同完整轴      -> 保持完整轴
singleton 与完整轴      -> 输出完整轴
多个不同完整轴          -> DomainError
全部输入都是 singleton  -> 继续输出 singleton
```

资产数量相同不代表轴相同。多个完整轴必须同时匹配 `asset_type + codes 顺序 + axis_fingerprint`。singleton 的业务来源可以不同：单资产选择保留真实单代码，截面/member reduce 使用匿名 singleton；普通数值运算只依赖其 `N=1` 广播能力。

专用规则覆盖 shape-changing operator：

| Domain rule | 典型 operator | 输出变化 |
|---|---|---|
| `asset_reduce_domain` | `cs_mean/cs_sum/cs_std`、`member_mean/member_sum/member_std` | `N -> 1`，`codes=None` |
| `step_reduce_domain` | `step_mean/step_sum/step_std`、`step_corr`、`intraday_flat_*` | `S -> 1` |
| `same_asset_domain` | `neutralize`、`group_*`、`member_demean/zscore` | 要求相同具名完整资产轴 |
| `get_step_domain` | `get_step` | 选择位置并保留 singleton step |
| `slice_step_domain` | `slice_step` | 按实际 slice 长度更新 step_count |
| `select_by_pos_domain` | `select_by_pos` | 保持维度并更新资产代码或 step_count |
| `lookup_by_col_domain` | `lookup_by_col` | 输出继承 mapping 的目标资产轴 |

### 5.8 显式 Domain 转换 operator

只有用户显式写出的频率转换才 Lower 为对应 operator：

```text
align_frequency(..., method="ffill")
  align_frequency

显式 resample
  resample

资产/指数选择
  __select_asset -> 通用 select_by_pos
```

普通 operator 和输出边界使用 NumPy singleton 广播；Compiler 不为它们插入物理扩展节点。

内部 helper lowering 与公开算子编译规则的职责分别是：

- `_lower_align_frequency()`：只接受完整标准粗分钟 step 轴，首版只支持 `method="ffill"`，生成细频 step 位置索引；
- `_lower_select_asset()`：在编译期把稳定资产代码解析为当前冻结轴上的位置，Runtime 只执行通用 keepdims slice。
- `_lower_resample()`：校验细到粗或分钟到日频转换及 `mean/sum/std/last`，推导新 Domain，并把原始频率加入 Runtime 参数。

### 5.9 输出 Domain 校验

每个输出在编译完成后仍保留自己的原生 `TermDomain`。`_validate_output_domain()` 不要求它与任务 Domain 完全相等，只放行明确的广播情况：

```text
scalar 输出
  domain=None 的纯标量输出直接拒绝

calendar
  必须与 target 完全一致

asset
  N=1 可广播到 target N
  N>1 必须与 target 的 asset_type/codes/fingerprint 完全一致

frequency
  同频率可接受
  1d + step=1 可作为 singleton 广播到分钟 target
  其他跨频率必须显式转换

step_count
  只能是 1 或 target_step_count
```

这一步只证明最终 `np.broadcast_to()` 合法，不创建广播数组，也不替用户决定 PIT、延迟、报告期或重采样方法。

## 6. 物理规划与 Runtime

文件：[`execution.py`](../src/factor_engine/execution.py)

### 6.1 PhysicalPlanner

```text
PhysicalPlanner.partitions(job, options)
  -> chunk_size 为空：整个输出日期区间一个分区
  -> chunk_size 存在：按输出日期顺序切分
  -> 在 provider calendar 中定位每个分区
  -> 向前扩展 job_lookback 个日期
  -> 生成 ReadDomain(dates, write_dates, codes, steps, output_slice)
  -> PhysicalPartition
```

`dates` 包括 lookback，`write_dates` 只包括该分区真正输出的日期。`output_slice` 表示这个 chunk 应写入完整输出数组的位置。

PhysicalPlanner 创建的 `ReadDomain` 以任务输出坐标为起点；随后 Provider 在 `bind_many()` 中为每个 `SourceTerm` 换成它自己的原生 `codes` 和 `steps`。因此日频 Source 不会因为任务目标是分钟频就被要求返回分钟 step，指数 Source 也不会因为目标是股票就被要求返回股票资产轴。

### 6.2 source binding 和 load group

每个分区开始时：

```text
plan.source_terms
  -> provider.bind_many(source_terms, read_domain)
      -> 每个 SourceTerm 恰好一个 SourceBinding
         ├── term_id
         ├── source_spec
         ├── source 自己的 read_domain
         ├── load_group_key
         └── value_kind（默认 NUMERIC）
  -> Runtime 按 load_group_key 分组
```

`SourceBinding` 是逻辑计划到本分区物理读取的桥。Provider 可以让多个 source 共享一个 `load_group_key`，Runtime 便只调用一次 `load_many(group)`；怎样把这次调用实现成一个 SQL、一次文件扫描或逐字段 fallback，是 Provider 内部职责。

Runtime 会校验 `bind_many()` 是否恰好覆盖全部 SourceTerm，也会校验每次 `load_many()` 返回的 term id 集合是否准确。

### 6.3 DAG 拓扑执行

```text
for term_id in plan.topological_order:
  LiteralTerm
    -> np.float64 literal

  SourceTerm
    -> 若所在 group 尚未加载，provider.load_many(group)
    -> 校验 dtype=float64 和精确 shape
    -> 同组结果一起放入 workspace

  OperatorTerm
    -> 从 workspace 取得输入
    -> 无名数据输入按位置传参，具名数据输入按关键字传参，
       字面量配置作为 params 展开
    -> OperatorSpec.func(*args, **keyword_inputs, **params)
    -> 按 TermDomain 校验原生结果 shape
    -> inf 转为 NaN
    -> 写回 workspace
    -> 递减输入 reference count
    -> 删除不再被引用且不是输出的输入
```

`reference_counts` 由 Compiler 预先计算。Runtime 不做运行时 DAG 分析，只按计划维护 workspace 生命周期。`ExecutionStats` 当前记录：

- `load_calls`：物理 load group 调用次数；
- `peak_workspace_values`：workspace 同时持有的最大值数量；
- `released_terms`：执行中提前释放的 Term；
- `provider_events`：DataProvider 上报的诊断事件，由 `stream()` 挂载。

operator 结果校验针对的是该 Term 的原生 Domain，而不是最终任务 Domain：

```text
expected native shape
  = (len(partition.read_domain.dates), term.domain.asset_count, term.domain.step_count)
```

例如 `member_mean()` 的 kernel 直接返回 `T × 1 × S`，Runtime 会按匿名 singleton Domain 校验这一小数组，不会提前扩展为 `T × N × S`。`member_demean()` 和 `member_zscore()` 属于 transform，仍返回完整资产轴。

### 6.4 产生 chunk

DAG 完成后，Runtime 对每个输出：

```text
workspace[output_term_id]
  -> 校验 write_dates 是读取日期的连续后缀，直接截取写出区间
  -> 保留输出 Term 的原生 N/S
  -> np.broadcast_to(values, partition target shape)
  -> 广播失败则 RuntimeExecutionError
  -> 数组设为只读
  -> ResultChunk(formula_id, output_slice, values)
```

最终广播允许两种 singleton：

- 资产轴 `T × 1 × S -> T × N × S`，例如单资产、单指数、截面统计和成员池 reduce；
- step 轴 `T × N × 1 -> T × N × S`，例如日频行情进入分钟目标或 step reduce 输出。

`np.broadcast_to()` 返回只读 view，不复制底层数据。只有 `compute()` 把 chunk 写入最终完整结果数组时才真正物化目标形状；流式消费者如果只继续做可广播计算，可以直接利用这个 view。同一个分区的多个公式共享 source load 和 DAG 计算。

## 7. 结果装配

### 7.1 ComputeResult

`BatchFactorEngine.compute()` 为每个 `formula_id` 延迟创建一个完整 `float64` 数组，然后按 `output_slice` 写入 chunk。

```text
ComputeResult
  ├── domain: ResolvedOutputDomain
  ├── arrays: formula_id -> T × N × S ndarray
  ├── plan: LogicalPlan
  └── stats: ExecutionStats
```

如果消费流时发生异常，已创建的结果数组会被清空并继续抛出异常。只有流自然结束才返回 `ComputeResult`。

`BatchResult` 当前只是 `ComputeResult` 的别名，不代表另一种结果协议。

### 7.2 DataFrame

```text
ComputeResult.to_dataframe()
  -> MultiIndex.from_product(dates, codes, steps)
  -> 每个 formula_id 成为一列
  -> 每个 T × N × S 数组按同一顺序 flatten
```

唯一默认布局是：

```text
index = (date, asset, step)
columns = formula_id
```

引擎默认返回数组；只有调用 `to_dataframe()` 时才构造 DataFrame。

## 8. DataProvider 三阶段契约

协议定义在 [`model.py`](../src/factor_engine/model.py)。内存 Provider 位于
[`providers.py`](../src/factor_engine/providers.py)，正式实现位于
[`data_provider/`](../src/factor_engine/data_provider/)。旧 Snapshot 适配层
（`FeatureStoreDataProvider`）已于 2026-08-18 移除，背景见
[`取数链路演进归档.md`](取数链路演进归档.md)。

```text
编译期：describe_many(SourceRefExpr[]) -> SourceRefExpr -> InputSpec
  回答“这个逻辑输入是什么 domain/type”

分区绑定期：bind_many(SourceTerm[], ReadDomain) -> SourceBinding[]
  回答“这个分区具体从哪里、按什么坐标读”

分区加载期：load_many(SourceBinding[]) -> term_id -> ndarray
  真正执行 I/O，并返回严格 float64 T × N × S
```

这是取数和编译的主要解耦点。Compiler 不调用 `load_many()`，Runtime 不重新解释公式 source 语义。

### 8.1 MemoryDataProvider

主要用于契约测试和小规模内存研究：

```text
describe_many()
  -> 使用显式 InputSpec；没有时从 feature key 和数组 shape 推导

bind_many()
  -> 根据 SourceTerm domain 生成 ReadDomain
  -> 使用可选 load_groups 生成 group key

load_many()
  -> 按日期和代码坐标切片
  -> 返回 float64 3D 数组
```

二维输入在构造 Provider 时补成 `T × N × 1`。

### 8.2 SmartQuantDataProvider

正式 Provider 的内部链路为：

```text
data_sources.json -> Catalog
SourceRef -> source 配置条目 -> InputSpec
bind_many -> SourceSpec/SourceBinding
load_many -> dataset batch reader -> OceanBase/DuckDB backend
          -> strict normalizer -> float64 T×N×S
```

它不调用 Store、DataRouter、SmartQuantSourceReader 或 FeatureArray。日频宽表和分钟
parquet 均按 LoadGroup 执行真正的多字段单次物理读取；Catalog、calendar、资产轴和
诊断只在当前任务生命周期内保存。

### 8.3 legacy DataRouter 调用链（仅供追溯）

文件：[`legacy/data/router.py`](../src/factor_engine/legacy/data/router.py)。
新管线不再有 Router 参与；以下链路只服务于 `factor_engine.legacy` 研究层。

```text
resolve_source(key) 固定优先级：
  1. memory_data
  2. 显式 source_overrides
  3. data_sources.json 中的配置记录
  4. 动态 data_dict 字段目录
  5. 否则失败

read_spec(spec, store, scope)
  -> cache key = SourceSpec + snapshot signature + scope signature
  -> source="store"  -> FeatureStore.load_feature()
  -> source="memory" -> _read_memory()
  -> 其他             -> SmartQuantSourceReader.read_source()
  -> 缓存并返回 FeatureArray
```

Router 返回旧数据设施中的 `FeatureArray`，只被 legacy `Executor` 消费。

## 9. Operator 调用链

文件：[`operators/registry.py`](../src/factor_engine/operators/registry.py)

`default_operator_registry()` 是 Compiler 和 Runtime 共用的 operator 语义表：

```text
OperatorSpec
  ├── name
  ├── func
  ├── input_kinds（或 VariadicInput）
  ├── output_kind
  ├── date_lookback
  ├── domain_rule（可为空，对应专属 lowering）
  └── optional_inputs
```

使用位置不同：

```text
Compiler
  使用 input/output kind、函数 signature、date_lookback 和 domain_rule
  不执行 func

Runtime
  根据 operator_name 找到同一个 OperatorSpec
  只执行 func 并校验返回 shape
```

公开 operator 按语义分文件：

```text
elementwise.py      标量/逐元素运算和 OperatorSpec
timeseries.py       日期轴、step 轴和日内窗口运算
cross_section.py    截面、分组和成员运算
alignment.py        显式坐标映射 kernel
domain_rules.py     编译期输出 Domain 推导规则
registry.py         名称、类型、lookback 和 domain_rule 注册
```

`resample` 和 `align_frequency` 与其他公开算子一起注册在默认 Operator Registry，
并分别使用专属 Domain lowering。资产选择最终执行通用 `select_by_pos`。普通广播
不对应 LogicalPlan 节点。

几个容易混淆的截面 operator 调用链如下：

```text
cs_mean/cs_sum/cs_std
  kernel: 沿资产轴 reduce，keepdims=True
  domain_rule: asset_reduce_domain
  native output: T × 1 × S，codes=None

member_mean/member_sum/member_std
  kernel: Numba 单次扫描成员池，直接写 T × 1 × S
  domain_rule: asset_reduce_domain
  不创建 T × N × S 中间统计数组

rank/cs_zscore/winsorize/neutralize
  kernel: 截面 transform
  native output: T × N × S

group_mean/group_sum/group_std/group_demean/group_zscore
  group code 作为普通 CODE 输入传入
  kernel 内分组并写回对应资产位置
  native output: T × N × S
```

选择单资产或指数时，helper 负责稳定代码语义，Compiler 负责 `code -> pos`，`select_by_pos` 只负责通用数组切片。行业分类同样由 helper/source 选择分类列，`group_*` kernel 不感知行业标准等业务语言。

## 10. 临时因子保存与再次引用

文件：[`repository.py`](../src/factor_engine/repository.py)

当前没有生产落盘需求，也没有生产可用的 FactorRepository。
`TemporaryFactorRepository` 只验证 ResultStream 的保存/失败语义和 `load_factor()` 闭环，
不得接入生产。

### 10.1 保存

```text
repository.save(engine.stream(request))
  -> 从 stream.plan.outputs 得到全部 factor_id
  -> 校验目标均不存在
  -> 创建一次 staging 目录
  -> 消费 ResultStream
     -> 每个 ResultChunk 写成 start_stop.npy
     -> 记录 chunk metadata
  -> stream.succeeded 必须为 True
  -> 为每个 factor 写 metadata.json
  -> os.rename() 提交到最终 factor 目录
  -> 返回 factor_ids
```

任何异常都会删除本次 staging；如果已有部分 factor 已提交，也会回滚这些本次提交的目录。当前目录格式、覆盖规则和并发语义都不是未来正式仓库标准。

### 10.2 再次引用

```text
公式 load_factor("alpha")
  -> SourceRefExpr("factor:alpha")

RepositoryDataProvider(base, repository)
  -> describe_many()
     factor: 前缀 -> repository metadata -> InputSpec
     普通 source  -> base.describe_many()
  -> bind_many()
     factor: 前缀 -> repository SourceBinding
     普通 source  -> base.bind_many()
  -> load_many()
     repository binding -> repository.load()
     普通 binding       -> base.load_many()
```

`RepositoryDataProvider` 是组合适配器，不改变 Compiler 或 Runtime。保存后的因子仍以普通 `SourceTerm` 进入下一次任务。

## 11. 错误阶段

主要错误类型用于指出失败发生在哪一层。公式解析与名称绑定层的错误定义在
`formula.py`（均继承 `FormulaError`），其余错误类型定义在 `model.py`：

```text
FormulaParseError / SymbolBindingError
  公式语法或名称作用域

CompileError
  helper、operator、参数或 lowering

DomainError
  日期、资产、频率、step 或坐标身份不合法

DataProviderError
  describe/bind/load 契约或物理数据不满足计划

RuntimeExecutionError
  operator 执行失败或输出 shape 不合法

ResultAssemblyError
  stream 未自然完成，不能装配或提交结果
```

Compiler 会尽量在错误消息中补充 `source:line:column` 和 `formula_id`。Runtime 包装 operator 异常时保留原异常作为 cause。

## 12. legacy 边界

```text
factor_engine 顶层公共 API
  -> 只导出新 FormulaBatch / Compiler / Runtime / Provider 契约

factor_engine.legacy
  -> Calculator / FeatureManager / FeatureRegistry 等旧研究层
  -> legacy/data/：FeatureStore / DataRouter / SmartQuantSourceReader 等旧数据设施
```

新 `BatchFactorEngine` 不调用 `legacy`。旧研究层与旧数据设施不应成为新增核心功能的入口；唯一允许的 legacy → 新核心方向依赖是旧 Reader 复用 `data_provider/backend` 的中性 SQL 后端、以及共用 `data_provider/data_sources.json` 目录配置。未来研究层应在 `FormulaBatch + ComputeRequest + DataProvider` 之上重新设计，而不是把 Registry/alias 生命周期重新塞回 Compiler。

## 13. Review 时建议重点核对的不可变条件

```text
公式层
  [ ] 每个公式的局部作用域隔离，最后一个 binding 是输出
  [ ] helper 在 LogicalPlan 前完全展开

编译层
  [ ] SourceRefExpr 只通过 InputSpec 参与编译
  [ ] LogicalPlan 不包含 SourceSpec 或物理 load group
  [ ] SourceTerm 保留 InputSpec 的原生 frequency 和 step_count
  [ ] 普通 operator 通过 numpy_domain 或专用 domain_rule 推导输出
  [ ] 不同完整资产轴不能因 shape 相同而混合
  [ ] 除 singleton 广播外，不同 frequency 必须显式转换
  [ ] 每个输出的原生 TermDomain 都能按确认规则广播到 ResolvedOutputDomain
  [ ] 公共表达式按语义身份合并
  [ ] lookback 沿 DAG 累计

物理层
  [ ] 分区 ReadDomain.dates 覆盖任务级 lookback
  [ ] bind_many 对每个 SourceTerm 恰好返回一个 binding
  [ ] load_many 严格返回 float64 T × N × S

执行层
  [ ] Runtime 只执行计划，不重新做公式或 domain 决策
  [ ] 每个 operator 返回值精确匹配自己的原生 TermDomain
  [ ] Term 在最后一次引用后释放
  [ ] 输出边界只使用 np.broadcast_to，不插入物理扩展算子
  [ ] ResultChunk 只包含 write_dates，已是目标 shape 且 values 只读

结果层
  [ ] ResultStream 只有自然结束才 succeeded
  [ ] compute 与 repository 都以完整消费 stream 为成功前提
  [ ] DataFrame 固定为 (date, asset, step) index × formula_id columns

边界
  [ ] 新核心不反向依赖 factor_engine.legacy
  [ ] 临时仓库格式不被当作正式仓库契约
```

|---|---|
| `factor_engine/__init__.py` | 新管线稳定公共 API，不能泄漏 legacy |
| `formula.py` | AST、Python 语法子集、名称绑定和 helper 表达 |
| `domain.py` | 频率/step 规则、日期规范化、稳定 hash 和轴身份 |
