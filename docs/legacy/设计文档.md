# core 设计文档

本文面向维护者和后续开发者，说明 `core/` 当前设计、模块边界、数据模型和维护方法。结论以源码为准，尤其以 `schema.py`、`store.py`、`engine.py`、`manager.py`、`data_router.py`、`sources.py`、`smartquant.py`、`ops.py` 为准。

## 1. 设计目标

`core` 的目标是把因子计算拆成四个稳定边界：

1. 用户只声明 `FeatureDef`，不手写取数、对齐和落盘流程。
2. 计算层只处理对齐后的三维数组，不知道 SQL、parquet 和业务 source 细节。
3. 取数层只负责把外部 source 读成 `FeatureArray`，不解释公式。
4. 存储层只管理 Snapshot 轴和已物化 feature，不读取外部 source，也不执行公式。

主路径是：

```text
FeatureManager.register(FeatureDef)
FeatureManager.materialize(key_or_alias)
  -> Calculator.cal_formula(...)
      -> FormulaParser
      -> Planner
      -> Executor
          -> FeatureStore / DataRouter
          -> ops
  -> FeatureStore.write_feature(...)
```

不推荐为同一件事添加第二条执行路径。新增能力优先挂到这条链路中的对应边界。

## 2. 数据模型

### 2.1 FeatureKey

`FeatureKey` 是逻辑命名模型：

```text
asset.freq.name
```

解析函数：

```python
parse_feature_key(key)
```

要求至少三段。第三段之后可以继续包含点，例如：

```text
stk.1d.industry_code.SW2021.L1
stk.1d.index_weight.CSI300
```

### 2.2 FeatureSpace

`FeatureSpace` 是物理空间模型：

```python
FeatureSpace(
    asset: str,
    freq: str,
    dates: np.ndarray,
    codes: np.ndarray,
    steps: int,
)
```

统一 shape：

```text
T x N x S
```

`FeatureStore.resolve_space(...)` 是唯一空间推导入口。不要在 reader、planner 或算子里自行拼接空间规则。

### 2.3 FeatureDef

`FeatureDef` 是用户声明的特征定义，字段包括：

- key、asset、freq、name
- alias
- formula
- params
- dependencies
- steps
- input_mask、sample_mask、output_mask
- delay_lf、delay_dict
- materialize、overwrite
- metadata

`FeatureManager.register(...)` 会把定义规范化：

1. 字符串公式解析成 Expr。
2. alias 冻结成完整 feature key。
3. mask 解析并冻结。
4. 从 formula 和 mask 中自动收集依赖。
5. `delay_dict` key 规范化为完整 feature key。
6. `formula`、mask 持久化为 `_expr_to_dict(...)` 的字典表示。

维护原则：

- 影响计算语义的字段必须进入 `FeatureDef.signature`。
- `metadata` 可以记录展示信息，但不要把核心计算语义只放在 metadata 中。
- 需要持久化的新 Expr 类型必须同时维护 `_expr_to_dict(...)` 和 `_expr_from_dict(...)`。

### 2.4 SourceSpec

`SourceSpec` 是 Router 和 Reader 之间的取数协议：

```python
SourceSpec(
    asset,
    freq,
    name,
    source,
    table,
    field,
    params,
)
```

它描述“如何读取一个叶子 source”，不描述因子公式。

### 2.5 FeatureArray

`FeatureArray` 是计算和存储之间的数组容器：

- `key`
- `values`
- `space`
- `feature_def`
- `feature_meta`
- `missing_value`
- `metadata`
- `dims=("date", "asset", "step")`

`FeatureArray.__post_init__` 会校验 key、数组维度和 shape。二维数组会自动补成 `T x N x 1`。

## 3. 模块边界

### 3.1 schema.py

负责基础模型和频率规则：

- `FeatureKey`
- `FeatureSpace`
- `FeatureDef`
- `FeatureMeta`
- `SourceSpec`
- `FeatureArray`
- `ExecutionScope`
- 频率和 step 工具
- 稳定 hash

当前频率规则：

| freq | steps |
| --- | --- |
| `1d` | 1 |
| `1min` | 237 |
| `5min` | 48 |
| `15min` | 16 |
| `30min` | 8 |
| `60min` | 4 |

注意：`1min` step 是 `930..1129 + 1300..1456`，共 237 个；其他分钟频率基于完整 240 分钟会话起点抽样。

### 3.2 store.py

`FeatureStore` 负责 Snapshot 和物化存储：

- 初始化日期轴和资产轴：`init_snapshot(...)`
- 读取轴：`get_dates()`、`get_asset_codes(asset)`、`get_code_map(asset)`
- 空间推导：`resolve_space(...)`
- code 映射：`to_inner_code(...)`
- 判断和读取 feature：`has_feature(...)`、`load_feature(...)`、`load_feature_def(...)`
- 写入 feature：`write_feature(...)`
- chunk 写入事务：`begin_feature_write(...)`、`write_feature_chunk(...)`、`finalize_feature_write(...)`、`abort_feature_write(...)`
- 外部导入：`import_array(...)`、`import_dataframe(...)`
- manifest 修复：`rebuild_manifest_from_metadata()`

存储格式：

```text
snapshot/
  manifest.json
  axes/
    dates.npy
    assets/{asset}/inner_codes.npy
    assets/{asset}/code_map.parquet
  features/{asset}/{freq}/{name}/
    metadata.json
    data/{YYYYMMDD}.npy
    code/{YYYYMMDD}.npy
```

每日文件只保存非全缺失的资产行，读取时恢复到完整固定轴。

维护原则：

- `FeatureStore` 不应 import `DataRouter`。
- `FeatureStore` 不应执行公式。
- 轴不隐式扩展，`extend_asset_axis(...)` 当前显式拒绝。
- 写入 metadata 和 manifest 要保持原子性，chunk 写入必须使用 staging 目录。

### 3.3 engine.py

`engine.py` 是公式解析、规划和执行层。

主要类型：

- `Expr`
- `ConstExpr`
- `FeatureExpr`
- `AliasExpr`
- `OpExpr`
- `BroadcastIndexFeatureExpr`
- `RuntimeFeatureExpr`
- `FormulaParser`
- `Planner`
- `Executor`
- `Calculator`

职责拆分：

| 类 | 职责 | 不做什么 |
| --- | --- | --- |
| `FormulaParser` | 解析受限 Python 表达式语法 | 不访问 Store/Router |
| `Planner` | alias、资产/频率对齐、mask 注入、delay 改写 | 不读取 source，不执行算子 |
| `Executor` | 递归求值计划，读取叶子，调用 ops | 不推断业务语义 |
| `Calculator` | 组织 parse/plan/eval/write，维护 runtime feature | 不管理定义注册和依赖递归 |

Planner 的核心对齐规则：

- 同资产同频率：直接使用。
- 日频 leaf 进入分钟输出：按 `delay_lf` 或 `delay_dict` 做日期滞后，保留单 step，后续广播。
- 粗分钟进入细分钟：按 step index 前向填充。
- 细分钟进入粗分钟：禁止隐式聚合；新 batch pipeline 必须显式调用公开 `resample(...)`。
- `stk` 进入 `cb` 输出：通过 `cb.1d.underlying_stk_col` 做正股列映射。
- `idx` 进入非 `idx` 输出：必须显式 `broadcast_index_feature(...)`。

### 3.4 manager.py

`FeatureManager` 是用户层入口：

- 注册定义：`register(...)`
- alias 管理：`add_alias(...)`、`replace_alias(...)`、`remove_alias(...)`
- 解析定义：`resolve(...)`
- 重命名：`rename(...)`
- 列表和搜索：`list(...)`、`search(...)`
- 物化：`materialize(...)`
- 定义保存和加载：`save_definitions(...)`、`load_definitions(...)`

Helper：

- `get_lf(...)`
- `get_hf(...)`
- `get_fund(...)`

`materialize(...)` 当前有两种路径：

1. 全量路径：创建一个共享 `Calculator`，递归物化依赖并计算目标。
2. chunk 路径：按日期 chunk 构造 `ExecutionScope`，每个 chunk 使用一个 `Calculator`，最后提交 metadata 和 manifest。

chunk 限制：

- `workers` 必须为 `1`。
- 目标 `FeatureDef.materialize` 必须为 `True`。
- 对于注册依赖，如果依赖 `materialize=True` 但 Store 中缺失，chunk 模式会报错；chunk 中可复用的 runtime 中间依赖应设为 `materialize=False`。

### 3.5 data_router.py

`DataRouter` 负责把完整 key 解析成 `SourceSpec` 并读取临时 source。

解析优先级：

1. `memory_data`
2. `source_overrides`
3. `source_config["sources"]` 精确字典
4. `source_tables` 扫描出来的 `data_dict`

读取后缓存 key：

```text
stable_hash(SourceSpec.to_dict(), store.snapshot_signature, scope_signature(scope))
```

缓存同时包含 source 参数、Snapshot 签名和 scope，避免错误复用。

维护原则：

- Router 不写 Store。
- Router 不解释公式。
- Router 不做裸字段名的宽松匹配。
- 注册 override 时必须清理同 key 旧缓存。

### 3.6 sources.py

`sources.py` 管理 source metadata 和扫描逻辑：

- `INDEX_INNER_CODES`
- `DEFAULT_EXCLUDE_FIELDS`
- `fundamental_name(...)`
- `minute_data_type(...)`
- `minute_path(...)`
- `load_source_config(...)`
- `lookup_source_record(...)`
- `build_data_dict(...)`
- `source_spec_from_data_dict(...)`
- `source_spec_from_record(...)`
- table schema 扫描
- 基本面字段目录扫描

维护重点：

1. `INDEX_INNER_CODES`
   - 当前只有 `CSI300: 3145` 已确认。
   - `SSE50/CSI500/CSI1000/CSI2000` 为 `None`。
   - 新增指数广播或指数成分 source 时，先确认指数 `InnerCode`，再维护该字典或在 `data_sources.json` 里用精确 source 配置。

2. `DEFAULT_EXCLUDE_FIELDS`
   - 用于扫描 `source_tables` 时排除非业务字段。
   - 新表增加了文件名、更新时间、标识列等字段时，应加入排除列表或表级 `exclude_fields`。

3. `source_tables`
   - 表级配置只负责扫描字段并恢复 `SourceSpec`。
   - 多条配置命中同一 key 会报歧义错误。

4. `sources`
   - 精确配置用于特殊 source、特殊参数或特殊字段名。
   - 例如复权因子、不可交易、转债正股映射、指数成分、行业字段。

### 3.7 smartquant.py

`SmartQuantSourceReader` 是外部 source reader。

当前支持的 `SourceSpec.source`：

| source | 方法 | 来源 |
| --- | --- | --- |
| `ReturnDaily` | `_daily_field` | `SmartQuant.ReturnDaily` |
| `CBReturnDaily` | `_daily_field` | `SmartQuant.CBReturnDaily` |
| `IndexQuote` | `_index_quote_field` | `JYDB.QT_IndexQuote` |
| `Fundamental` | `_fundamental` | `SmartQuant.Fundamental_Item{data_code}` |
| `Signal` | `_signal` | `Signal.runner_value_{runner_id}` |
| `MinuteParquet` | `_minute_field` | parquet + DuckDB |
| `Untradable` | `_untradable` | `SmartQuant.Untradable` |
| `AdjustFactor` | `_adjust_factor` | `JYDB.DZ_AdjustingFactor` |
| `IndexComponentWeight_Choice` | `_index_component` | `SmartQuant.IndexComponentWeight_Choice` |
| `CBStockMap` | `_cb_stock_map` | `JYDB.Bond_ConBDBasicInfo` |

维护原则：

- 新 source 类型先在 `read_source(...)` 分派，再添加私有读取方法。
- 读取方法返回 `FeatureArray`，通常通过 `align.feature_from_frame(...)` 或 `align.feature_array(...)`。
- 所有日期范围来自 `store.resolve_space(spec, scope=scope)` 和 `align.date_bounds(...)`。
- SecuCode 到 InnerCode 的转换使用 `store.to_inner_code(...)`。
- 不要在 reader 中写 Store。

### 3.8 align.py

`align.py` 把外部数据对齐为 `FeatureArray`：

- `feature_from_frame(...)`：日频或普通长表对齐。
- `feature_from_intraday_frame(...)`：分钟长表对齐。
- `feature_array(...)`：已对齐数组封装。
- `normalize_value_column(...)`：数值字符串和分类值编码。
- 日期格式工具。

维护原则：

- 对齐只使用 Snapshot 的固定 `dates` 和 `codes`。
- 无法映射到 Snapshot 轴的数据被忽略或由上层决定是否报错。
- source metadata 应写入 `FeatureArray.metadata`，便于落盘后追踪。

### 3.9 ops.py

`ops.py` 是纯数组算子库：

- 不读取配置。
- 不访问 Store。
- 不访问 Router。
- 不知道 key、asset、freq、SourceSpec。
- 输入输出都应是 NumPy 可处理对象。

公式可调用的算子必须注册到：

```python
default_operator_registry()
```

新增算子维护步骤：

1. 在 `ops.py` 中实现纯函数。
2. 如果需要 shape 统一，先调用 `ensure_3d(...)`。
3. 如果涉及两个三维数组 step 兼容性，调用 `_check_step_compatible(...)`。
4. 对 rolling/window 参数做正数校验。
5. 对 bool、整数、缺失值语义做显式处理。
6. 在 `default_operator_registry()` 中注册。
7. 如果算子改变资产、频率或 step 语义，覆盖对应 `OperatorSpec` 字段。
8. 如果算子影响 chunk overlap，在 `engine.infer_date_overlap(...)` 中维护推断规则。
9. 如果算子应接受 `sample_mask` 注入，在 `engine.SAMPLE_AWARE_OPS` 中维护位置。
10. 更新用户手册的算子表和调用链文档。

当前 Numba kernel 用于：

- group 统计
- member 统计
- step corr
- intraday rolling

## 4. data_sources.json 维护

配置结构：

```json
{
  "source_tables": [
    {
      "asset": "stk",
      "freq": "1d",
      "source": "ReturnDaily",
      "table": "SmartQuant.ReturnDaily"
    }
  ],
  "sources": {
    "stk.1d.adj_factor": {
      "asset": "stk",
      "freq": "1d",
      "name": "adj_factor",
      "source": "AdjustFactor",
      "table": "JYDB.DZ_AdjustingFactor",
      "field": "adj_factor",
      "params": {}
    }
  }
}
```

### 4.1 新增普通表字段

如果字段在已有 `source_tables` 对应表中，通常无需新增精确配置。`DataRouter` 初始化时会扫描表 schema，排除默认字段后生成 `data_dict`。

检查方式：

```python
router.search("FieldName")
router.resolve_source("stk.1d.FieldName")
```

### 4.2 新增特殊 source

如果字段需要特殊读取逻辑或参数，放入 `sources` 精确字典：

```json
"stk.1d.my_special": {
  "asset": "stk",
  "freq": "1d",
  "name": "my_special",
  "source": "Signal",
  "table": "Signal.runner_value_123",
  "field": "runner_value",
  "params": {"runner_id": 123}
}
```

### 4.3 新增分钟 parquet 配置

`MinuteParquet` 表级配置依赖：

- `asset`
- `freq`
- `source="MinuteParquet"`
- `data_type`
- `path_template`
- `sample_date`
- `date_col`
- `date_col_type`

示例：

```json
{
  "asset": "stk",
  "freq": "1min",
  "source": "MinuteParquet",
  "table": "/data/cephfs/minute/one_minute_stat/{date}.parquet",
  "data_type": "one_minute_stat",
  "path_template": "/data/cephfs/minute/one_minute_stat/{date}.parquet",
  "sample_date": "2024-12-31",
  "date_col": "trading_day",
  "date_col_type": "date"
}
```

`scan_minute_parquet_fields(...)` 会用 DuckDB 读取 sample parquet schema。

## 5. 扩展指南

### 5.1 新增 source 类型

步骤：

1. 在 `SmartQuantSourceReader.read_source(...)` 增加 `source` 分派。
2. 实现 `_your_source(...)`，返回 `FeatureArray`。
3. 优先用 `feature_from_frame(...)`、`feature_from_intraday_frame(...)` 或 `feature_array(...)` 对齐。
4. 在 `data_sources.json` 中新增精确 source 或表级配置。
5. 如需搜索，维护 `scan_source_table_fields(...)` 或额外扫描逻辑。
6. 写最小 smoke test：`router.resolve_source(...)` 和 `router.read(...)`。

### 5.2 新增公式 helper

公式 helper 是解析阶段的语法糖。步骤：

1. 在 `engine.py` 中实现 Python helper，返回 Expr。
2. 在 `_expand_formula_helpers(...)` 中加入 helper 名称。
3. 如 helper 有字面量参数，使用 `_literal_helper_arg(...)` 统一校验。
4. 如 helper 引用 feature key，返回 `FeatureExpr(...)` 或已有 helper 组合。
5. 更新 `normalize_registered_expr(...)` 或 key 解析逻辑，确保定义可持久化。

### 5.3 新增 Expr 类型

只有在普通 `OpExpr` 无法表达时才新增 Expr 类型。步骤：

1. 定义 dataclass。
2. `FormulaParser` 或 helper 中构造它。
3. `Planner._rewrite(...)` 支持它。
4. `Executor._eval(...)` 明确执行或保证 Planner 前消除。
5. `_expr_to_dict(...)` / `_expr_from_dict(...)` 支持持久化。
6. `format_expr(...)` 支持 debug 输出。
7. 注册阶段 `normalize_registered_expr(...)` 支持冻结。

### 5.4 新增频率

频率规则集中在 `schema.py`：

- `SUPPORTED_INTRADAY_FREQS`
- `_INTRADAY_MINUTES`
- `get_freq_step_count(...)`
- `get_freq_step_values(...)`
- `get_resample_group_index(...)`
- `get_ffill_step_index(...)`

新增频率时还要检查：

- `sources.minute_data_type(...)`
- `data_sources.json`
- `MinuteParquet` 路径和 step 标签
- Planner 的频率改写规则
- 用户文档和调用链

### 5.5 新增指数

如果需要 `broadcast_index_feature(index="...")`：

1. 确认指数在 `idx` Snapshot 轴中的 `InnerCode`。
2. 在 `sources.py::INDEX_INNER_CODES` 填入映射。
3. 如需要成分和权重，在 `data_sources.json["sources"]` 新增：
   - `stk.1d.index_weight.{INDEX}`
   - `stk.1d.is_member.{INDEX}`
4. 检查 `SmartQuant.IndexComponentWeight_Choice` 是否可用 `IndexInnerCode` 或 `IndexCode` 过滤。
5. 用 `store.resolve_space("idx.1d.__space__")` 和 `space.code_to_pos(...)` 验证。

## 6. 运行时和 chunk 设计

### 6.1 Runtime feature

`Calculator` 内部有：

```python
runtime_features: dict[str, FeatureArray]
```

`materialize=False` 的结果只保存在当前 `Calculator` 会话中，不写 Store。当前 `FeatureManager.materialize(...)` 的全量路径使用同一个 `Calculator` 递归计算依赖，因此 runtime 中间结果可以被最终因子复用。

chunk 模式下每个 chunk 都创建新的 `Calculator`，runtime 生命周期只覆盖当前 chunk。

### 6.2 ExecutionScope

`ExecutionScope` 包含：

- `read_dates`
- `write_dates`
- `chunk_id`

作用：

- Store 读取只加载 `read_dates`。
- Source 读取只读 `read_dates` 覆盖的 SQL/parquet 范围。
- chunk 写入只写 `write_dates`。
- Router cache 把 scope signature 纳入缓存 key。

### 6.3 overlap 推断

`engine.infer_date_overlap(...)` 当前识别：

- `delay(axis=0)`：增加 `periods`
- `ts_mean/ts_sum/ts_std/ts_min/ts_max(axis=0)`：增加 `window - 1`
- `intraday_flat_mean/std`、`intraday_by_step_mean/std`：增加 `window_days - 1`

如果新增日期窗口算子，必须维护该函数，否则 `chunk_size` 自动 overlap 可能不足。

## 7. 维护约定

### 7.1 保持单一职责

- 新取数逻辑放 `smartquant.py` 或独立 reader，不放 `store.py`。
- 新数组计算放 `ops.py`，不放 `engine.py`。
- 新用户声明 helper 放 `manager.py` 或 `engine.py` helper，不放 reader。
- 新 source metadata 放 `data_sources.json` 或 `sources.py`。

### 7.2 兼容性

当前 `FeatureStore` 明确拒绝旧 manifest schema。升级存储格式时需要：

1. 提升 `MANIFEST_SCHEMA_VERSION`。
2. 编写显式迁移工具。
3. 不在读取路径里静默兼容旧格式。

### 7.3 错误要早报

已有代码倾向显式报错：

- source 歧义报 `ValueError`
- 资产/频率无法自动对齐报 `ValueError`
- 未配置指数 InnerCode 报 `KeyError`
- Snapshot 轴不一致报 `ValueError`
- Store 已存在且未覆盖报 `FileExistsError`

新增功能应延续这种风格。

### 7.4 文档同步
