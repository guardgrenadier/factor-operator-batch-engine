# ADR 0001：分离数据路由与公式执行

- 状态：已接受
- 日期：2026-07-23

## 背景

当前主链路在 `Executor` 递归求值叶子节点时，依次尝试 runtime feature、`FeatureStore` 和 `DataRouter`。因此执行过程同时承担表达式求值、数据位置发现和数据读取。

新系统需要同时支持交互式研究、字符串公式批量计算和自动因子挖掘。后两种场景不应要求预先注册 `FeatureDef`，并需要更明确的批量调度、内存控制和失败诊断。

## 决策

公式编译与执行内核不负责把逻辑数据 key 路由到数据库、表或文件。

编译结果必须显式声明叶子输入需求。应用编排层或数据准备组件负责解析这些需求并建立输入绑定。执行器只消费已绑定输入，不再通过隐式 fallback 链寻找数据。

数据可以按执行分区延迟加载；“与路由分离”不等价于“运行前必须把全部数据一次性装入内存”。具体预取和分区协议将在后续 ADR 中决定。

## 理由

- 同一执行内核可以服务研究前端和无 `FeatureDef` 的批任务。
- 执行前可以完整检查依赖、估算 lookback 和安排分块。
- 数据读取失败与算子执行失败可以产生不同的结构化诊断。
- 调度器可以统一复用叶子数据和公共子表达式。
- 多进程 worker 不需要持有数据库路由和研究定义状态。

## 影响

- 当前 `Executor._load_feature_like()` 的 Store/Router fallback 不再属于目标架构。
- `DataRouter` 可以保留为研究平台或基础设施适配器，但不被执行内核直接依赖。
- 需要定义 `InputRequirement`、数据规格和 `InputBinding` 协议。
- 需要决定绑定由任务级编排器一次完成，还是由调度器按 chunk 完成。

## 尚未决定

- 计算域的完整字段。
- 输出空间的声明或推导规则。
- 数据绑定是数组、迭代器、共享内存句柄还是统一 provider 接口。
- 批内缓存与跨任务缓存的生命周期。
