# core 当前调用链

- 更新日期：2026-07-30
- 对应状态：`FeatureRegistry`、`ExecutionRequest`、`SourceExpr` 第一阶段实现
- 范围：描述当前 `core/` 实际代码，不描述 `docs/refactor/` 中的远期方案

本轮设计说明见
[`fix/feature-registry-execution-request-source-expr.md`](fix/feature-registry-execution-request-source-expr.md)。

## 1. 当前推荐入口

当前研究定义的注册和执行分成两个动作：

```python
from core import ExecutionRequest, FeatureDef, FeatureManager

manager = FeatureManager("/path/to/snapshot")

definition = manager.registry.register(
    FeatureDef.from_key(
        "stk.1d.alpha",
        alias="alpha",
        formula="divide(stk.1d.ma5, stk.1d.ma20)",
    )
)

result = manager.execute(
    ExecutionRequest(
        target="alpha",
        materialize=True,
        overwrite=False,
        return_array=True,
    )
)
```

入口职责如下：

```text
FeatureDef
  只描述研究定义和计算语义

FeatureRegistry.register()
  规范化定义、冻结 alias、自动收集依赖、维护定义索引

FeatureManager.execute(ExecutionRequest)
  解析目标、调度依赖、选择 full/chunk、决定是否物化

Calculator.calculate()
  解析、规划、执行表达式，只返回 CalculationResult

FeatureStore
  提供固定计算空间、读取已有数组、持久化最终结果
```

`FeatureManager` 不再重复提供仅转发参数的 `register()`、`resolve()` 或
`materialize()`；定义操作直接通过 `manager.registry` 完成。

## 2. 总体调用链

### 2.1 定义注册

```text
FeatureDef
  -> FeatureRegistry.register()
     -> 校验 key 与 asset/freq/name 一致
     -> 解析 formula 和 masks
     -> 将当前可见 alias 解析为 canonical FeatureExpr
     -> 收集全部 FeatureExpr dependencies
     -> 校验 SourceExpr 和 delay_dict
     -> 校验 definition alias
     -> 写入 Registry 内存状态
```

### 2.2 非分块执行

```text
ExecutionRequest
  -> FeatureManager.execute()
     -> Registry.resolve(target)
     -> 递归计算未物化的已注册 dependencies
     -> Calculator.calculate()
        -> FormulaParser
        -> Planner
        -> Executor
           -> runtime result / FeatureStore / DataRouter
        -> CalculationResult
     -> Manager 根据 materialize 决定是否写 FeatureStore
     -> Manager 根据 return_array 决定是否返回结果
```

### 2.3 分块执行

```text
ExecutionRequest(chunk_size=...)
  -> FeatureManager._execute_chunked()
     -> 推断或采用 overlap
     -> FeatureStore.begin_feature_write()
     -> 对每个日期块：
        -> 建立 ExecutionScope(read_dates, write_dates)
        -> 新建 Calculator
        -> 递归依赖并计算 read_dates
        -> 只写 write_dates 到 staging
     -> FeatureStore.finalize_feature_write()
     -> 可选地重新加载完整结果
```

### 2.4 显式外部输入

```text
SourceExpr(SourceSpec)
  -> Planner 保留 source 身份并完成空间改写
  -> Executor._load_source()
     -> FeatureStore 已有同 key 数组：直接加载
     -> 否则：DataRouter.read_spec(SourceSpec)
        -> memory 或 SmartQuantSourceReader
```

这条路径取代了 fundamental 通过 `dependencies` 充当 flag、再由 bridge 临时注册
DataRouter source 的旧路径。

## 3. 核心对象契约

### 3.1 FeatureDef

`FeatureDef` 当前包含：

```text
身份
  key, asset, freq, name

研究语义
  alias, params, metadata

计算语义
  formula, dependencies, steps
  input_mask, sample_mask, output_mask
  delay_lf, delay_dict
```

以下内容已经不属于 `FeatureDef`：

```text
materialize
overwrite
signature
```

`dependencies` 虽然仍是序列化字段，但调用方不再通过 `from_key()` 提供它。
Registry 会用规范化后的公式和 masks 重新派生依赖，传入对象中的旧值不会成为执行依据。

当前仍可用 `FeatureDef.from_key()` 构造定义。未来会由其他定义对象承接构造入口，并把
alias 从 definition 中拆出；这是未来 breaking change，不属于本轮代码。

### 3.2 ExecutionRequest

当前请求是单目标请求：

```python
ExecutionRequest(
    target="stk.1d.alpha",  # 也可传 Registry alias
    materialize=True,
    overwrite=False,
    chunk_size=None,
    overlap=None,
    return_array=True,
)
```

参数只表达调度策略，不进入 Calculator 的计算语义：

- `target`：已注册 canonical key 或 alias。
- `materialize`：是否由 Manager 将最终目标写入 Store。
- `overwrite`：物化时是否允许覆盖。
- `chunk_size`：启用日期分块；当前分块必须物化。
- `overlap`：显式指定向前读取的日期数；省略时由表达式推断。
- `return_array`：是否将最终数组返回调用方。

构造时会拒绝不能生效的组合：

- 空目标；
- 非正 `chunk_size`；
- 负 `overlap`；
- `materialize=False, overwrite=True`；
- `materialize=False, return_array=False`；
- `materialize=False` 的分块执行；
- 没有 `chunk_size` 却指定 `overlap`。

当前没有 `workers` 配置，分块按单 worker 串行执行。

### 3.3 CalculationResult

Calculator 返回轻量计算结果：

```python
CalculationResult(
    key=...,
    values=...,          # T x N x S ndarray
    space=...,           # FeatureSpace
    missing_value=...,
    diagnostics=...,
)
```

它不携带研究 `FeatureDef`，也不负责持久化。Manager 需要写 Store 时才把结果转换为
带当前 definition 的 `FeatureArray`。

### 3.4 FeatureArray 与 FeatureSpace

计算和存储层仍统一使用 `T x N x S`：

```text
T = date
N = asset code
S = step
```

二维输入会补成 `T x N x 1`。数组形状必须与 `FeatureSpace.shape` 完全一致。

### 3.5 FeatureExpr 与 SourceExpr

两种叶子表达式含义不同：

```text
FeatureExpr("stk.1d.close")
  普通逻辑依赖
  可来自本次 runtime、FeatureStore 或 DataRouter 的常规 key 解析
  会被 Registry 收集进 dependencies

SourceExpr(SourceSpec(...))
  带完整取数参数的显式外部输入
  优先复用 Store，否则严格按该 SourceSpec 读取
  不进入 dependencies
```

因此 `SourceExpr` 的参数不是 `params`/`metadata` 中的提示，而是可序列化公式语义。

## 4. FeatureRegistry 调用链

### 4.1 初始化

Manager 默认在以下目录创建 Registry：

```text
<snapshot>/feature_defs/
```

也可以通过 `FeatureManager(..., definitions_dir=...)` 指定目录。

`FeatureRegistry(root)` 会加载：

```text
root/<asset>/<freq>/<name>.json
```

alias 只保存在各自 definition JSON 中。Registry 加载时重新建立
`alias -> canonical key` 内存索引，不存在独立 `aliases.json`。

Registry 不从 FeatureStore metadata 恢复当前定义，也不会在 `get()` 或 `resolve()` 时
回退到 Store。Store 中的 `FeatureDef` 只是某次物化结果的历史快照。

### 4.2 register

```python
registered = registry.register(definition)
```

顺序如下：

1. 规范化 canonical key。
2. 校验 `key` 与 `asset/freq/name` 一致。
3. 将字符串、Expr 或已序列化 dict 统一转换为 Expr。
4. 用当前 Registry alias 索引解析公式中的 `AliasExpr`。
5. 对三个 mask 做相同规范化。
6. 从所有 `FeatureExpr` 收集 canonical dependencies。
7. 收集并校验 `SourceExpr`；同一 source key 不允许对应冲突的 SourceSpec。
8. 将 `delay_dict` 的 alias 解析成 canonical key，并校验它确实属于公式输入。
9. 校验新 alias 是非关键字标识符且全局唯一。
10. 原子写入 definition 和 alias 派生索引。

同一个 key 重复 `register()` 会失败；Registry 不猜测两个定义是否计算等价，也不自动
合并不同 key 的相同公式。

### 4.3 alias 冻结

alias 只在定义注册时解析：

```text
base -> stk.1d.base

注册 derived(formula="multiply(base, 2)")
  -> derived.formula 内保存 FeatureExpr("stk.1d.base")
  -> derived.dependencies 保存 "stk.1d.base"
```

之后把 `base` 修改为 `renamed_base` 不会改写已经注册的 `derived`。这使 alias 变更不会
悄悄改变已有定义含义。

alias 只能指向已注册 definition；一个 definition 只能有零个或一个 alias。基础操作为：

```python
registry.add_alias(key, alias)
registry.update_alias(key, alias)
registry.remove_alias(key)
```

这些操作同步更新 `FeatureDef.alias` 和派生索引。冲突操作失败时保留原状态。

### 4.4 replace 与 remove

```python
registry.replace(new_definition)
registry.remove(key)
```

- `replace()` 要求 canonical key 已存在，替换定义并删除旧 alias 索引。
- `remove()` 删除定义及其 alias 索引。
- 两者都不会删除、覆盖或重新计算 Store 中已有数组。
- Registry 当前不维护反向依赖图，因此不会级联删除依赖方。

### 4.5 save 与 load

Registry 状态是内存态，定义变更后由调用方显式执行：

```python
registry.save()
```

`save()` 写出当前定义，并移除 definitions 目录中已经不属于当前 Registry 的 JSON。
`load()` 整体重建 definitions 和 alias 索引；加载中任一定义失败时恢复加载前的内存状态。

## 5. Manager 非分块执行

### 5.1 解析目标

```python
feature_def = manager.registry.resolve(request.target)
```

请求目标必须已注册。即使 Store 已经存在同名数组，也不能用未注册 key 作为
`manager.execute()` 的目标。

### 5.2 递归计算 definition dependencies

Manager 为一次非分块请求建立一个 Calculator，并递归处理目标定义：

```text
dependency 是当前目标自身
  -> 跳过

dependency 已在 Calculator.runtime_features
  -> 跳过

dependency 已注册，且 Store 中不存在
  -> 递归计算，结果只放进本次 runtime_features

其他 dependency
  -> 不由 Manager 递归
  -> 后续由 Executor 从 Store 或 DataRouter 读取
```

因此“已注册”只表示 Manager 知道如何计算它；它并不要求依赖在注册目标之前已经物化。
递归计算的中间 definition 默认不会写 Store，只有请求的最终 target 受
`materialize` 控制。

递归过程中会检测循环依赖并抛出错误。

### 5.3 调用 Calculator

Manager 将已规范化 definition 的以下计算字段传给 Calculator：

```text
formula
input_mask / sample_mask / output_mask
delay_lf / delay_dict
feature_def（仅用于解析目标空间）
ExecutionScope（仅分块时存在）
```

`ExecutionRequest.materialize/overwrite/return_array` 不会传入 Calculator。

### 5.4 物化与返回

Calculator 返回 `CalculationResult` 后：

```text
materialize=True
  -> Manager 转成 FeatureArray
  -> FeatureStore.write_feature(overwrite=request.overwrite)

return_array=True
  -> 返回 CalculationResult

return_array=False
  -> 返回 None
```

无论成功失败，非分块请求结束时 Manager 都清空 DataRouter 会话缓存。

## 6. Calculator、Planner 与 Executor

### 6.1 Calculator

`Calculator.calculate()` 接受一个字符串或 Expr：

```python
result = calculator.calculate(
    "divide(stk.1d.ma5, stk.1d.ma20)",
    output="stk.1d.factor",
)
```

它依次：

1. 用 FormulaParser 解析字符串。
2. 用 Planner 做空间、延迟和 mask 改写。
3. 用 Executor 递归求值。
4. 校验结果空间。
5. 构造 `CalculationResult`。
6. 将结果放入本 Calculator 的 `runtime_features`。
7. 返回结果。

Calculator 不写 Store，不注册 FeatureDef，不修改 alias。

### 6.2 FormulaParser

公式语法基于 Python expression AST，当前支持：

- 数值、布尔值等常量；
- `+ - * /`；
- 单目负号；
- 单次比较；
- 简单函数调用；
- 字面量关键字参数；
- `asset.freq.name` 形式的 dotted feature key。

普通裸名称会先成为 `AliasExpr`。Registry 注册阶段负责把研究 alias 冻结为
`FeatureExpr`；直接调用 Calculator 时没有 Registry alias 表，因此未解析裸名称会失败。

### 6.3 Planner

Planner 负责：

- 解析表达式 alias（Registry 已规范化定义时通常已无 alias）；
- 根据 output 的 asset/freq 做跨资产、跨频率改写；
- 将本次已有的输出改写为 runtime feature；
- 应用低频 delay 和 `delay_dict`；
- 注入 input/sample/output mask；
- 规划重采样、指数广播等节点。

Planner 不读取数组，也不持久化结果。

### 6.4 Executor

Executor 递归执行已规划表达式：

```text
ConstExpr
  -> 直接返回常量

FeatureExpr
  -> _load_feature_like()

SourceExpr
  -> _load_source()

RuntimeFeatureExpr
  -> 从 runtime_features 取本次中间结果

OpExpr
  -> 递归求值参数并调用 OperatorSpec.func
```

执行结束时，Executor 用 Store 的固定 snapshot 解析目标 `FeatureSpace`，将可合法广播的
`T x N x 1` 扩展到目标 steps，并拒绝其他形状不一致。

## 7. 叶子数据读取顺序

### 7.1 普通 FeatureExpr

`Executor._load_feature_like(key)` 的固定顺序是：

```text
1. 当前 eval 的 leaf cache
2. Calculator.runtime_features
3. FeatureStore 中已物化数组
4. DataRouter.read(key)
5. 均不可用则报错
```

DataRouter 的普通 `read()` 会按下列优先级解析 key：

```text
memory_data
-> source_overrides
-> source_config 中的显式 record
-> data_dict/source_tables
-> KeyError
```

### 7.2 显式 SourceExpr

`Executor._load_source(spec)` 的固定顺序是：

```text
1. 当前 eval 的 source leaf cache
2. FeatureStore 中是否存在 spec.key
3. DataRouter.read_spec(spec)
4. 没有 DataRouter 则报错
```

显式 SourceSpec 不经过 `resolve_source(key)` 再猜一次取数参数。

DataRouter cache key 包含：

```text
SourceSpec.to_dict()
FeatureStore.snapshot_signature
ExecutionScope signature
```

所以同 key、不同参数或不同日期 scope 不会误用同一份缓存。Manager 在请求或 chunk
结束时调用 `clear_cache()`。

## 8. fundamental 当前调用链

```python
definition = get_fund(
    "Revenue",
    column_name="value",
    quarters=4,
    name="revenue_4q",
)
manager.registry.register(definition)
result = manager.execute(
    ExecutionRequest(target=definition.key, materialize=False)
)
```

完整链路：

```text
get_fund()
  -> fundamental_name(...) 生成 raw source key
  -> 构造 SourceSpec(
       source="Fundamental",
       field=...,
       params={
         column_name,
         quarters,
         data_code,
         publ_date_limit,
       },
     )
  -> formula = SourceExpr(spec)
  -> FeatureDef.dependencies 保持为空

Registry.register()
  -> 序列化并校验 SourceExpr

Manager.execute()
  -> Calculator -> Planner -> Executor._load_source()
     -> Store 已有 raw source：复用
     -> 否则 DataRouter.read_spec(spec)
        -> SmartQuantSourceReader.read_source()
```

`Fundamental_ItemN` 形式的 field 会在未显式提供 `data_code` 时提取 `N`。原来的
fundamental bridge 和“往 dependencies 写 key 作为取数 flag”的行为已经删除。

## 9. get_lf、get_hf 与 get_fund

三个 helper 现在只构造 `FeatureDef`，不执行注册、不计算、不物化：

```text
get_lf()
  -> 普通 FeatureExpr
  -> 可选复权和停牌 mask 表达式

get_hf()
  -> 普通 FeatureExpr

get_fund()
  -> 显式 SourceExpr(SourceSpec)
```

helper 不接收 `dependencies`、`materialize` 或 `overwrite`。返回值仍需交给
`manager.registry.register()`。

## 10. 分块执行细节

分块请求必须 `materialize=True`。Manager 先确定 overlap：

```text
request.overlap 有值
  -> 直接使用

request.overlap 为 None
  -> Planner 规划目标表达式
  -> infer_date_overlap(planned)
  -> 加上需要 runtime 递归计算的 definition dependency overlap
```

每个 chunk 的 scope：

```text
write_dates = 当前块实际写出的日期
read_dates  = write_dates 之前额外带 overlap 的日期 + 当前块
```

Calculator 在 `read_dates` 上计算；Store 只从结果中截取 `write_dates` 写入 staging。
每个 chunk 使用新的 Calculator，避免 runtime 结果跨 scope 复用。

写入过程：

```text
begin_feature_write()
  -> 创建 staging 目录，尚不提交 metadata/manifest

write_feature_chunk()
  -> 按日写 data/code 文件

finalize_feature_write()
  -> 全部 chunk 成功后写 metadata
  -> 原子切换目录并更新 manifest

异常
  -> abort_feature_write()
  -> 删除 staging，保留原有正式结果
```

如果 `return_array=True`，finalize 后从 Store 加载完整特征并包装为
`CalculationResult`；否则返回 `None`。

## 11. Store 与 Registry 的边界

两者都可能保存 FeatureDef，但含义不同：

```text
FeatureRegistry definition
  当前有效研究定义
  可 register/replace/remove
  是 alias 和当前公式的事实来源

FeatureStore metadata.feature_def
  数组物化时的定义快照
  用于解释和校验该份历史结果
  不参与 Registry resolve
```

Manager 物化时使用 Registry 中当前 definition 构造 `FeatureArray`，Store 随结果写入该
definition 快照。Registry replace 不会让旧数组自动失效或重算；当前也没有 signature
比较或自动等价判断。

## 12. 绕过研究层直接计算

底层 Calculator 已经可以绕过 FeatureRegistry，连续计算多个全 key 输出：

```python
from core import Calculator

calculator = Calculator(store, data_router=router)

ma5 = calculator.calculate(
    "ts_mean(stk.1d.close, 5)",
    output="stk.1d.ma5",
)
ma20 = calculator.calculate(
    "ts_mean(stk.1d.close, 20)",
    output="stk.1d.ma20",
)
factor = calculator.calculate(
    "stk.1d.ma5 / stk.1d.ma20 - 1",
    output="stk.1d.factor",
)
```

前两次输出会进入同一个 Calculator 的 `runtime_features`，第三次可以直接复用，不要求
创建或注册 FeatureDef，也不会写 Store。

当前尚未提供以下多行文本前端：

```text
ma5 = ...
ma20 = ...
factor = ...
```

也尚未提供 `close`、`ma5` 这样的 request-local 裸名称绑定。现阶段直接计算必须使用
合法的完整 output key，并在后续公式中以 dotted key 引用。未来多行入口应复用当前
Calculator/Planner/Executor，不把局部变量注册成 Registry alias。

## 13. 当前错误边界

常见失败点及责任对象：

```text
定义 key 字段不一致
  -> FeatureRegistry.register/replace

重复 definition key 或 alias
  -> FeatureRegistry

公式中存在未知研究 alias
  -> FeatureRegistry 规范化或 Planner

delay_dict 指向非公式输入
  -> FeatureRegistry

循环 definition dependency
  -> FeatureManager

目标未注册
  -> FeatureRegistry.resolve

叶子既不在 runtime/Store 也不能由 Router 读取
  -> Executor/DataRouter

算子不存在
  -> Executor

结果形状与目标空间不一致
  -> Executor/CalculationResult

目标已物化且 overwrite=False
  -> FeatureStore
```

## 14. 本轮明确删除或不再推荐的路径

以下路径不属于当前 API：

- `FeatureManager.register()`；
- `FeatureManager.materialize()`；
- Manager 自己维护 definitions/aliases 双份状态；
- 从 Store 恢复当前 Registry alias；
- 独立 `aliases.json`；
- 调用方或 helper 手写 `dependencies`；
- fundamental dependency flag；
- fundamental 到 DataRouter 的临时 bridge；
- `Calculator.calc_formula()` 负责保存数组；
- `FeatureDef.materialize/overwrite/signature`；
- 为单一实现增加 Executor interface、DataProvider interface 或 factory；
- 只做参数转发的 Manager 包装方法。

## 15. 当前测试覆盖

与本调用链直接相关的测试包括：

- Registry alias 增加、修改、删除和冲突原子性；
- replace 清除旧 alias；
- alias 冻结和 dependencies 自动派生；
- Registry definition/alias 持久化；
- SourceExpr 序列化和 fundamental 显式取数；
- fundamental 不再依赖 bridge；
- SourceExpr 优先复用 Store；
- Calculator 只返回数组结果且不物化；
- Manager 只物化最终目标，不物化 runtime dependency；
- `materialize=False` 只返回结果；
- full 与 chunk 结果一致；
- ExecutionRequest 无效组合校验。
