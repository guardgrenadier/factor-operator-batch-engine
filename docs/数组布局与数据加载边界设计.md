# 数组布局与数据加载边界设计

- 状态：已接受的目标设计；SQL Reader 二级结构待实现迁移
- 日期：2026-08-31
- 权威决策：[ADR-0001](adr/0001-use-positional-array-layout-for-operators.md)
- 详细设计：[Reader 与 Load 规范化边界](Reader与Load规范化边界设计.md)

本文对 Reader、Query Builder 和 Operator 结果校验的最新结论，优先于详细设计文档中
尚未同步的旧 Reader 候选清单。

## 1. 背景

当前实现同时存在两类复杂度：普通算子通过 `TermDomain/domain_rule` 检查资产、频率和
坐标身份；各 Reader、Normalizer 和 Runtime 又重复执行数组转换与校验。这样增加新算子
或数据集时，往往需要同时修改编译、读取和运行时多层代码。

本设计把责任收敛为四个边界：普通算子只处理数组布局；SQL Query Builder 只生成受约束
的物理查询；Reader 执行物理读取并返回 RawBatch；LoadNormalizer 负责 Source 数组进入
Runtime 前的唯一权威规范化。

## 2. 总体链路

```text
data_sources.json
  -> Catalog：DatasetSpec + SourceSpec
  -> Reader：按执行方式和结果布局读取 RawBatch
       -> SQL Reader：调用具名 Query Builder，执行规范 SQL 结果
       -> Fundamental Reader：执行 rank/PIT 查询并解码 step
       -> Parquet Reader / CBStockMap Reader：处理各自物理布局
  -> LoadNormalizer：转换、散布和校验
  -> NormalizedSourceBatch：float64 T × N × S
  -> Runtime：按位置执行 OperatorTerm
  -> OutputDomain：校验并广播最终物理 shape
```

`DataProvider.load_many()` 继续作为 Engine 可见的统一端口，但内部只编排 Reader、必要的
Query Builder 和 LoadNormalizer，不亲自实现每种数据集的转换规则。

## 3. 普通算子的数组布局契约

普通 OperatorTerm 使用 `ArrayLayout`，不再携带业务坐标身份：

- 输入是 scalar 或 `T × N × S` 数组；
- T 必须等于当前物理分区的日期长度；
- N、S 分别只要求相等或一侧为 1，由 NumPy 广播；
- 不比较资产类型、代码及顺序、frequency、calendar 或 axis fingerprint；
- 明确接受 shape 相同但业务坐标不同的逐位置计算；
- 最终结果只检查能否广播到 OutputDomain 的物理 shape。

改变 N/S 或确实依赖 Source 元数据的操作仍显式表达，例如资产选择、股票到转债投影、
step reduction、`resample` 和 `align_frequency`。这些操作使用有限的 layout effect 或
专属 lowering，不恢复普通算子的业务坐标兼容性检查。

该选择可能让错误的业务坐标组合静默计算；公式作者和数据产品契约负责保证位置含义，
引擎只保证数组运算合法。

### 3.1 资产维 shape 错误的诊断增强

当两个输入的 N 不相等且都不是 1 时，失败原因仍是数组无法广播，Compiler 应在
ArrayLayout 校验阶段报错。为了帮助定位常见的跨资产误用，错误分支可以从现有
SourceTerm/InputSpec 依赖中读取唯一、无歧义的资产类型，并给出类似诊断：

```text
Asset dimension mismatch: stk(N=5000) cannot broadcast with cb(N=800);
use an explicit mapping, selection, or reduction operator
```

这只是错误信息增强，不是资产类型兼容性规则：

- 不同资产类型但 N 相等时仍允许按位置计算；
- 任意一侧 N=1 时仍允许广播；
- 相同资产类型但 N 不可广播时仍报告普通 shape 错误；
- 复合表达式无法确定唯一资产来源时退回普通 shape 错误；
- 不为此把 asset type 放回 ArrayLayout、OperatorTerm 身份或 `domain_rule`。

首版继续使用 `CompileError`，不新增容易被理解为“不同资产类型一律非法”的
`AssetTypeMismatchError`。

## 4. Reader 与 SQL Query Builder 分层

Reader 不按“日频/高频”分类，因为 frequency 是数据语义，不是存储形态。Reader 也不应
因为 SQL 写法特殊就分裂：`adjust_factor` 和 `untradable` 的结果仍然是普通
`date + asset + values` labels 布局，它们的特殊性在于怎样构造 SQL，而不是怎样读取和
解释结果。

因此 SQL 数据采用两级函数注册表：

```text
READER_REGISTRY[DatasetSpec.reader](ReaderRequest) -> Iterator[RawBatch]

SQL_QUERY_BUILDERS[DatasetSpec.query_builder](ReaderRequest, aliases)
  -> SQL + 物理字段诊断信息
```

`sql_reader` 负责公共执行流程：

1. 为 LoadGroup 的值列分配稳定别名；
2. 调用具名 Query Builder 生成 SQL；
3. 通过统一后端执行并记录诊断；
4. 要求查询结果使用规范列名；
5. 为实际存在的物理行补充 Source constant；
6. 包装为 `labels` RawBatch。

Query Builder 只负责 SQL 构造，必须把结果转换为以下规范布局：

```text
DataDate
InnerCode
可选 Step
value_0, value_1, ...
```

Query Builder 不散布数组、不应用 default、不处理 dtype/Infinity/ValueKind，也不直接返回
NormalizedSourceBatch。这里的扩展者是数据源适配代码的作者，不是公式作者；首版只允许
代码内具名函数，不在 JSON 中接受任意 SELECT、WHERE、表达式或 SQL 模板。

### 4.1 首版 Reader 清单

| reader | coordinate_mode | 适用物理布局或语义 |
| --- | --- | --- |
| `sql_reader` | `labels` | 执行 Query Builder 已转换为 date + asset + values 的 SQL 结果 |
| `fundamental` | `labels` | 带 rank/PIT 语义的基本面长表，并把报告期 rank 解码为 step |
| `parquet_bars` | `flat` | 按日期分区、带 step 的 parquet bars |
| `cb_stock_map` | `static` | 无日期的转债到正股关系及任务股票轴位置投影 |

### 4.2 首版 SQL Query Builder 清单

| query_builder | 当前用途 | 受约束的特殊行为 |
| --- | --- | --- |
| `panel_fields` | ReturnDaily、CBReturnDaily、IndexQuote、行业字段、指数权重/成员 | 多字段/常量投影、交易标志和可选 selector |
| `adjust_factor` | AdjustFactor | 基于交易行和生效日的 as-of 相关查询 |
| `untradable` | Untradable | 多个具名交易状态列派生一个 mask 字段 |

`adjust_factor` 和 `untradable` 不再是 Reader。它们生成相同的规范 labels SQL 结果，然后
复用 `sql_reader` 的执行、诊断和 RawBatch 包装。

指数记录的“稀疏”以及缺失位置的 default 属于 Source 规范化语义，不是物理读取布局，
因此不建立 `sparse_sql_panel`。指数权重和成员使用 `panel_fields`：Reader 只对真实成分
行投影 Weight 或成员常量 1，LoadNormalizer 再把缺失成员位置保留为 default 0。

### 4.3 Fundamental 为什么保留独立 Reader

Fundamental 的差异不只是多一段 WHERE 条件，还包括：

- `quarters` 和 `publ_date_limit` 共同决定物理行集合与 LoadGroup 兼容性；
- PIT 披露窗口和报告期 rank 是该数据模型的固定语义；
- `EndDateRank` 必须解码为 RawBatch 的 step 坐标；
- ItemCode 动态发现由 Catalog expander 完成，不是普通字段扫描。

因此不把 Fundamental 降格为 `sql_reader` 的任意过滤配置，也不建设通用 SQL 条件 DSL。
它继续使用具名 `fundamental` Reader；内部可以复用 SQL 执行辅助函数，但 rank/PIT 和 step
解码契约由该 Reader 自己负责。

### 4.4 CBStockMap 为什么保留独立 Reader

CBStockMap 的特殊性同时存在于结果结构和任务依赖，而不仅是 SQL：

- 物理关系没有 date，返回 `static` RawBatch；
- 首版只允许 S=1，并由 LoadNormalizer 沿整个 T 轴广播；
- `inner_code` 投影保留原始 StockInnerCode；
- `axis_position` 投影依赖本任务已冻结的股票资产轴，找不到时产生 NaN。

通用 `sql_reader` 的规范结果是 date + asset labels，无法在不引入额外投影/广播钩子的
情况下诚实覆盖上述行为。首版保留具名 `cb_stock_map` Reader 更简单。如果未来出现第二种
无日期静态关系，再从真实重复中提取 `static_relation_reader + relation_query_builder`，
而不是现在预建通用框架。

### 4.5 配置与扩展边界

- 已有 DatasetSpec 增加普通字段：只增加或扫描 SourceSpec；
- 新 SQL 数据集符合已有 Query Builder：配置 `sql_reader` 和对应 builder；
- 新 SQL 只需要特殊计算但仍输出规范 labels：新增具名 Query Builder，不新增 Reader；
- 新数据具有新的物理结果布局或坐标解码：新增 Reader 及其契约测试；
- LoadGroup 兼容键包含 Dataset、Query Builder 及影响物理行集合/坐标解码的共享参数，
  不因 field、constant、default 或 ValueKind 拆组；
- Reader 和 Query Builder 选择只存在于 DatasetSpec，不进入公式或 Term 的语义身份；
- 不提供万能 `custom` Reader、任意 SQL DSL、Reader 类层级或插件框架。

## 5. LoadNormalizer 是唯一 Source 校验边界

Reader 返回坐标列或位置提示以及原始值列，不分配最终数组，也不执行 ValueKind、缺失值
或最终 shape 校验。LoadNormalizer 独占以下职责：

- 按 ReadDomain 解析并校验日期、资产和 step 位置；
- 拒绝重复、越界或无法解析的坐标；
- 分配并散布到最终 `T × N × S`；
- 转换为 `float64`，将 NULL、缺失记录和正负 Infinity 统一为 `NaN`；
- 校验 MASK 的 `0/1/NaN` 与 CODE 的整数/NaN；
- 应用显式默认值和静态日期广播；常量列由 Reader 为实际存在的物理行投影；
- 返回只读且 term_id 集合完整的 NormalizedSourceBatch。

ValueKind 只声明有限值的逻辑集合，不负责 Infinity 策略。Runtime 信任已经规范化的
Source 数组，只检查返回的 term_id 集合，不再重复扫描 dtype、shape、Infinity 或
ValueKind。该信任只覆盖 Source Load 边界，不自动延伸到 Operator kernel 的返回值。

### 5.1 保留 Operator 结果契约校验

当前保留 `_validate_operator_result()`。算子执行可能产生错误 shape、非预期 dtype、
Infinity、非法 MASK 值、非整数 CODE，或者返回与编译期 layout 推导不一致的 scalar/数组。
因此每个 OperatorTerm 执行后仍需要独立的物理结果契约边界：

- 转换为运行时要求的 `float64`；
- 校验 scalar 与数组形态；
- 校验结果是否匹配编译期推导的物理 shape；
- 校验 MASK 的 `0/1/NaN` 与 CODE 的整数/NaN；
- 将 NUMERIC 的正负 Infinity 转换为 NaN。

该校验只防御算子实现违反数组和值契约，不恢复普通算子的资产类型、代码顺序、frequency、
calendar 或 axis fingerprint 检查。内置 operator kernel 仍应直接把非法数学结果写为 NaN；
未来只有在性能测量证明全数组扫描成为瓶颈，并且 kernel 契约已有充分测试时，才单独评估
是否减少 NUMERIC Infinity 扫描，本轮不修改这一边界。

## 6. 组件责任

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| Catalog | 数据集、字段、Reader、Query Builder 和值语义配置 | 物理读取和数组散布 |
| SQL Query Builder | 生成具名 SQL，并把结果列约束为规范 labels 布局 | 执行查询、任意 SQL DSL、数组散布 |
| Reader | 执行物理读取、解释结果坐标、流式返回 RawBatch | 最终数组和值协议 |
| LoadNormalizer | Source 坐标、shape、dtype、missing、ValueKind | 业务算子计算 |
| Compiler | ValueKind、参数、lookback、ArrayLayout 和 shape 失败诊断 | 普通输入的业务坐标一致性 |
| Operator 结果校验 | 算子返回值的 dtype、shape、Infinity 和 ValueKind 契约 | 普通输入的业务坐标一致性 |
| Runtime | 执行 DAG、Workspace 生命周期、Operator 结果校验和最终输出 shape | 重复校验已规范化 Source |

## 7. 迁移验收

- 普通算子不再依赖 `domain_rule` 或中间 TermDomain；
- 相同 shape、不同业务坐标的输入可以按位置计算；
- 不同资产类型且 N 不可广播时，编译错误包含两侧资产类型、N 和显式转换建议；
- 相同 N 或 singleton 广播不会因为资产类型不同而失败；
- 普通 SQL 面板、AdjustFactor 和 Untradable 共用 `sql_reader`，SQL 差异由具名
  Query Builder 承担；
- Fundamental 保留具名 Reader，不退化为可配置 SQL 过滤条件；
- CBStockMap 保留具名 static Reader，任务轴位置投影不塞进通用 SQL Reader；
- 同一 Reader 和 Query Builder 组合的新数据集能够只通过配置接入；
- Query Builder 测试验证 SQL 与规范结果列，Reader 测试验证执行和 RawBatch，
  Normalizer 测试集中验证数组协议；
- 每个 Source 数组只在 LoadNormalizer 中做一次完整规范化与校验；
- `_validate_operator_result()` 继续校验 Operator 的物理 shape、dtype、Infinity 和 ValueKind，
  但不执行普通输入的业务坐标校验；
- whole-domain、chunked 和多字段 LoadGroup 的结果保持一致。
